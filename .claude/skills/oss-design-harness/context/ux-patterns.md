# UX Patterns (PT) — 0·B단계 참조

## 이 문서를 쓰는 법

B단계는 후보를 만들기 전에 **독립 축**을 먼저 나눈다. 이 문서는 그 두 곳에 쓰인다.

1. **축 식별** — `core-problem.md`의 문제 구조를 읽고, 그 구조를 가르는 패턴이 여러 개인 지점이 곧 축이다.
2. **후보 생성** — 축마다 여기 등록된 패턴을 후보 시드로 쓴다. 여기 없는 패턴을 후보로 올려도 되지만,
   그때는 이 문서에 새 PT를 추가하고 같은 스키마로 기록한다.

## 작성 규칙

1. **5필드 고정** — 푸는 문제 / 형태 / 성립 조건 / 무너지는 조건 / 대안 패턴.
2. **성립 조건에 숫자를 넣는다** — "항목이 많을 때"가 아니라 "행 3~8 × 열 3~8". 숫자가 없으면
   하네스가 어떤 상황에도 그 패턴을 고를 수 있게 되어, 패턴 목록이 아니라 장식이 된다.
   **성립하는 최소 폭을 반드시 명시한다** — 이 하네스의 산출물은 모바일 화면이므로,
   데스크톱 폭을 요구하는 패턴은 등록은 되되 **후보 자격이 없다**(`PT-02`가 그런 경우다).
   B-3에서 후보로 올리기 전에 `DESIGN.md`의 `mobile.minViewportWidth`에 대입해 거른다.
3. **무너지는 조건이 없는 패턴은 등록하지 않는다** — 모든 상황에서 좋은 패턴은 없다.
   이 필드가 비어 있으면 그 패턴을 충분히 안 써봤다는 뜻이다.
4. **대안 패턴 상호 참조** — 같은 문제를 푸는 패턴끼리 서로를 가리키게 한다. 이게 B단계의 후보 집합이 된다.
5. **근거 태그** — 실제로 만들어봤는지, 남의 화면에서 봤는지, 추측인지 구분한다.

## B단계 리포트 형식 (하네스가 지킬 것)

`decisions.md`의 후보 표에 PT ID를 인용한다. ID 없는 후보는 어디서 왔는지 추적되지 않는다.

```
| 후보 | 설명 | 비교 근거 | 선택 |
| B. 가용성 매트릭스 [PT-02] | 행=사람, 열=후보일 | ... | ✅ |
```

## PT-01 — 행동 큐 (Action Queue)

- **푸는 문제**: 서로 다른 상태의 항목이 다수 동시에 흐르는데, 사용자가 "지금 무엇을 해야 하는지" 스스로 계산해야 하는 상황. 조회 실패가 아니라 **행동 누락**이 실패 모드일 때.
- **형태**: 홈의 기본 뷰가 달력도 목록도 아닌, "당신의 행동을 기다리는 것"만 모은 단일 리스트. 각 줄은 *원인*(왜 떴는가)과 *다음 행동*(무엇을 누르면 되는가)을 함께 담는다.
- **성립 조건**: 동시 진행 항목 15건 이상 / 상태 종류 3~6 / 행동 신호의 출처가 2종 이상(마감·무응답·충돌 등)으로 흩어져 있을 것. **최소 폭: 모바일** — 한 줄에 원인과 다음 행동을 담으므로 좁은 폭에서도 성립한다.
- **무너지는 조건**: 항목이 10건 이하면 전체 목록을 그냥 보는 게 낫다(큐가 목록의 부분집합이 되어 화면만 하나 늘어난다). 신호 종류가 1종이면 그냥 정렬이면 된다. 큐가 항상 비어 있거나 항상 20줄이면 둘 다 실패다.
- **대안 패턴**: `PT-03`(상태 보드 — 상태 소유가 목적이고 행동 촉구는 부차적일 때), 단순 마감순 정렬 목록.
- **근거**: 청첩장모임 스케줄러 실측 — 수십 건의 조율이 서로 다른 상태로 동시에 흐르는데 상태 소유 주체가 없는 구조

## PT-02 — 가용성 매트릭스 (행=사람, 열=선택지)

- **푸는 문제**: 여러 사람의 응답을 **교차 비교**해야 결정이 나는 상황. 그리고 **무응답 자체가 중요한 정보**일 때.
- **형태**: 행에 사람, 열에 선택지(날짜 등), 셀에 3~4값 상태. 열 하단에 집계 행을 붙여 결정을 즉시 내리게 한다. 무응답은 값이 아니라 **빈 셀**로 두어 시각적으로 튀게 한다.
- **성립 조건**: 행 3~8 × 열 3~8 (한 화면에 스크롤 없이 들어오는 크기). 셀 상태가 4값 이하. **최소 폭: 데스크톱.**
- **무너지는 조건**: 행이나 열이 10을 넘으면 스크롤이 생겨 교차 비교라는 유일한 장점이 소멸한다. 응답률이 100%에 가까우면 빈 셀 신호가 무의미해져 단순 목록이 낫다.
- ⚠️ **이 하네스에서는 후보 자격 없음** — 성립 조건이 데스크톱 폭을 요구한다. 모바일에서 같은 문제를 풀려면 아래 대안 패턴(날짜별 리스트 + 참석자 뱃지)으로 간다. 실측 근거가 있으니 항목은 남기되, B-3에서 후보로 올리지 않는다.
- **대안 패턴**: 날짜별 리스트 + 참석자 뱃지(교차 비교 포기, 모바일 가능), 캘린더 히트 오버레이(개인별 식별 포기, 기간이 길 때).
- **근거**: 청첩장모임 스케줄러 실측 — 일정 조율 축에서 채택된 패턴. 후보 3~6개 × 인원 3~6명이 한 화면에 들어가고, 무응답이 빈 셀로 시각적으로 튄 것이 채택 사유

## PT-03 — 상태 보드 (Status Board)

- **푸는 문제**: 다수 항목이 서로 다른 단계에 흩어져 있고, 실패 모드가 행동 누락이 아니라 **조회 실패**(어디 있는지 모름)일 때.
- **형태**: 상태를 섹션(모바일) 또는 열(데스크톱)로 자르고 모든 항목을 소속 상태 아래 배치한다. 항목은 상태 사이를 이동한다.
- **성립 조건**: 상태 종류 **3~7**, 총 항목이 스크롤 **3화면 이내**(모바일 2줄 행 72dp 기준 ≈ **24행**). **최소 폭: 모바일 — 단 세로 섹션 형태에 한해.** 가로 칸반은 360px에서 한 칸만 보여 불가.
- **무너지는 조건**: 한 섹션이 화면 높이를 넘으면 그 섹션 안에서 다시 "뭐부터"를 사람이 계산해야 한다 — 보드를 쓴 이유가 사라진다. 상태가 8종 이상이면 섹션 헤더가 화면의 절반을 먹는다.
- **대안 패턴**: `PT-01`(행동 촉구가 목적일 때).
- **근거**: 이식(Linear 보드 뷰 관찰 + 국내 웨딩 준비 앱의 카테고리 홈). **픽셀 임계(24행)는 미실측 발명값** — 청첩장모임 스케줄러 A단계에서 20/30건 더미로 검증 예정.

## PT-04 — 희소 슬롯 스트립 (Scarce Slot Strip)

- **푸는 문제**: 항목이 유한하고 미리 알려진 **슬롯**을 두고 경합하며, 실패 모드가 **충돌 또는 자리 소진**일 때. 조회 대상이 항목이 아니라 **남은 자리**다.
- **형태**: 슬롯을 시간 순서로 세로 나열하고 배정된 항목을 슬롯 아래에 붙인다. **빈 슬롯을 지우지 않는다** — 빈 것이 곧 정보다. 미배정 항목은 스트립 밖 별도 패널에 쌓고 각 줄에 다음 행동을 붙인다.
- **성립 조건**: 슬롯 총수가 **유한하고 30 이하**(스크롤 3화면 이내), 슬롯당 항목 **0~3개**, 마감이 **고정**이어서 슬롯이 늘어나지 않을 것. **최소 폭: 모바일** — 세로 나열, 격자 금지.
- **무너지는 조건**: 슬롯당 항목이 4개를 넘으면 슬롯 경계가 무너져 그냥 목록이 된다. **미배정 패널이 스트립보다 길어지면 축이 뒤집혀 있는 것**이므로 `PT-01`이 맞다 — 도입 초기에는 대개 이 상태이므로 **초반 구간에서 자기 조건에 걸리는 패턴**이다. 슬롯이 무한(마감 없음)이면 스크롤 끝이 없어진다.
- **대안 패턴**: `PT-01`(행동 촉구가 목적), `PT-03`(단계 소유가 목적).
- **근거**: 이식 변형(Todoist의 격자 밖 패널 + Airbnb 2층 구조의 상하 반전). **미실측** — A단계 검증 필요.

## PT-05 — 다중선택 일괄 배정 (Bulk Assign)

- **푸는 문제**: 다수 항목을 소수 목적지에 나눠 담는데, **어떤 부분집합을 만들지는 사람만 안다** — 기계가 규칙을 근사할 수 없을 때.
- **형태**: 리딩 체크박스가 상시 노출된 리스트 + 상단 컨텍스추얼 앱바(선택 개수·해제) + 하단 액션 바 → 목적지 시트. **개수와 탈출구는 위, 실행은 아래.**
- **성립 조건**: 항목 **30건 이상** / 한 번에 고르는 부분집합 **2~10** / **목적지 종류 30 이하** / 최소 폭 **360px** / 세션당 여유 시간이 **분 단위**.
- **무너지는 조건**: 목적지가 30을 넘으면 시트 탐색이 새 문제가 된다. **세션이 수십 초면 총 탭 수가 세션 수를 넘어 작업이 끝나지 않는다.** 항목당 목적지가 평균 2를 넘으면(= 커버링) 재선택 비용이 폭발한다.
- **대안 패턴**: `PT-06`(반복 축이 목적지 쪽일 때), `PT-07`(분류 규칙을 기계가 가질 수 있을 때).
- **근거**: 이식(Google Photos 다중선택 + M3 selection mode + PatternFly bulk selection). 규범 수치 근거 있음(행 56/72/88dp, 터치 타깃 48dp, 타깃 간 8dp).

## PT-06 — 목적지 고정 부착 (Pinned Destination)

- **푸는 문제**: **목적지 전환보다 항목 부착이 훨씬 잦아**, 매 배정마다 목적지를 다시 고르는 것이 비용의 대부분일 때. `PT-05`의 반복 축을 뒤집은 것이다.
- **형태**: 하단에 목적지 핀 바가 **상시** 고정되고, 핀이 걸린 동안 항목 행 탭 = 즉시 부착. 핀 교체가 곧 해제다. 핀 바에 **진척 카운트**가 함께 산다.
- **성립 조건**: 목적지 1개당 항목 **2개 이상** / 목적지 전환 : 부착 = **1:3 이상** / **부착이 가역**일 것 / 모드 표시 대역 2곳 / 최소 폭 **360px**.
- **무너지는 조건**: **부착이 비가역이면 모드 오조작이 치명상**이 된다 — 이 패턴은 되돌릴 수 있는 부착에만 쓴다. 목적지당 항목이 1개면(전부 1:1) 핀의 손익분기 아래다. 항목 행에 다른 주 동작(상세 열기)이 이미 있으면 제스처가 충돌하므로 좌측 48dp를 체크박스에 내주고 8dp를 띄워야 한다.
- **대안 패턴**: `PT-05`(전환이 드물 때), 드래그 앤 드롭(모바일 부적합).
- **근거**: 이식 변형 — PatternFly의 "액션 후 선택 유지"에서 **유지 대상을 선택이 아니라 목적지로 옮긴 것**. 손익분기 비율(1:3)은 미실측 발명값.

## PT-07 — 제안 검수 큐 (3지선다 포함)

- **푸는 문제**: 분류 규칙을 기계가 근사할 수 있지만 **확신이 낮은 경계 사례가 반드시 남고**, 그 사례를 강제로 한쪽에 넣으면 실패 비용이 클 때.
- **형태**: 앱이 초안 그룹을 만들되 **확정과 시각적으로 구분된 상태**로 두고, 경계 사례만 하단 카드로 **한 건씩** 묻는다. 응답은 2지선다가 아니라 **3지선다**(A에 / B에 / **아직 모르겠다**). 보류는 잔여 카운트에 계속 합산된다. **일괄 확정 명령을 만들지 않는다** — 만드는 순간 검수가 건너뛰어진다.
- **성립 조건**: 분류 신호가 항목당 1개 이상 존재 / 제안 정확도 **60% 이상** / 신호 1종당 항목 15개 이하 / 경계 사례가 전체의 **10~30%** / 최소 폭 **360px**(카드 1장).
- **무너지는 조건**: 신호가 없으면 콜드 스타트로 화면이 빈다. 정확도가 60% 아래면 수정 비용이 수동보다 커진다. 경계 사례가 50%를 넘으면 큐가 곧 전수 검사다. **큐는 끝나는 작업이라 소진 후 화면의 존재 이유가 사라진다** — 홈으로 쓰면 안 된다.
- **대안 패턴**: `PT-01`(신호가 상시 재생산될 때), `PT-05`(규칙을 못 만들 때).
- **근거**: 이식 — Google Photos 얼굴 병합 제안의 `Not sure` + Spotify Smart Shuffle의 "제안 ≠ 확정" 상태 분리. **반례로 Apple Photos**(보류 없는 Yes/No)가 애매한 항목을 강제 배정하는 것을 확인.

## 축 후보 목록 (AX)

B단계에서 반복적으로 등장하는 독립 축. 프로젝트마다 다시 뽑되, 여기 있는 것부터 검토한다.
축은 **서로 독립**이어야 한다 — 한 축의 선택이 다른 축의 선택을 강제하면 둘은 같은 축이다.

| ID | 축 | 양 끝 | 무엇이 이 축을 여는가 |
|---|---|---|---|
| AX-01 | 비주얼 무드 | 장식적 ↔ 기능적 | 도메인의 정서적 맥락이 있는가 |
| AX-02 | 정보 밀도 | 한 화면에 다 보임 ↔ 접고 파고들기 | 역할별 작업량이 비대칭인가 |
| AX-03 | 네비게이션 구조 | 탭바(병렬) ↔ 스택·허브(순차) | 주 작업이 여럿인가 하나인가 |
| AX-04 | 작업의 주도권 | 사람이 다 정한다 ↔ 앱이 제안하고 사람이 고친다 | 분류·배정 규칙을 기계가 근사할 수 있는 신호가 있는가. 있으면 축이 열리고, 없으면 `사람` 끝단 하나뿐이라 축이 아니다 |

**폼팩터는 축이 아니다.** 이 하네스는 모바일 하네스이고, 폼팩터는 0단계에서 이미 정해진 제약이다.
`AX-02`는 "데스크톱 ↔ 모바일"이 아니라 **모바일 뷰포트 안에서** 정보를 얼마나 접는가로 읽는다.
데스크톱 폴백을 후보로 만들지 않는다.

축을 나누지 않고 화면 전체를 통째로 비교하면, 무엇 때문에 선택했는지 뒤섞여(confound) 판단 근거가 남지 않는다.

# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP(`use_figma`)로 실제 **모바일** 화면을 만드는 하네스.
**이 파일은 뼈대만 있는 빈 템플릿입니다.** 각 단계의 `TODO`를 채우는 것이 곧 이 스킬을 만드는 작업입니다.

순서를 그대로 따라가는 것이 아니라, 아래 4단계가 각각 무엇을 판단해야 하는지에 집중합니다.

## 폼팩터는 축이 아니다

이 하네스의 산출물은 **모바일 화면**이다. 폼팩터는 B단계에서 후보를 벌려볼 대상이 아니라
0단계에서 이미 정해진 제약이고, 모든 단계가 그 위에서 굴러간다.

- **0단계** — 가정 로그의 `플랫폼`은 "모바일"에서 시작해 iOS/Android/크로스플랫폼까지 좁힌다. 데스크톱 폴백을 만들지 않는다.
- **B-1** — `AX-02`는 "데스크톱 ↔ 모바일"이 아니라 **모바일 뷰포트 안에서의 정보 밀도** 축으로 읽는다.
- **B-3** — `PT`의 성립 조건에 데스크톱 폭이 필요한 패턴은 후보 자격이 없다. 조건을 확인하지 않고 올리면 A단계에서 프레임 폭으로 걸린다.
- **B-3.5** — 목업 3안은 `DESIGN.md`의 `mobile.designViewportWidth` 후보 폭으로 그린다. 데스크톱 폭으로 그리면 이 단계가 잡으려던 문제를 그대로 B-4로 넘긴다. `MB-03`.
- **B-4** — `DESIGN.md`의 `mobile:` 블록(뷰포트·세이프에어리어·터치 타깃·본문 최소 크기·네비 구조)은 비워둘 수 없다. `DS-07`.
- **A** — 터치 타깃·세이프에어리어·프레임 폭은 노드 좌표로 판정된다. 눈이 필요 없다.
- **C** — 스크린샷은 `DESIGN.md`의 `designViewportWidth` 실제 크기로 렌더한다. 축소 렌더로 판정하지 않는다.

`ai-slop.md`의 판정식 중 데스크톱 랜딩을 전제한 것(3열 카드·통계 배너 등)은 모바일에서
같은 것이 **세로로 쌓인 형태**로 나타난다. 형태가 아니라 그 항목이 진단하는 성질로 본다.

## 참조 문서 (`context/`)

단계별 판단 기준은 이 파일이 아니라 `context/` 아래에 규칙 단위로 있다. **해당 단계 시작 전에 Read한다.**

| 파일 | 쓰는 단계 | 담는 것 | ID |
|---|---|---|---|
| `context/reference-channels.md` | 0 · B-2 | 레퍼런스를 어느 창구로 가져오는가, 채널별 사각지대 | `CH-nn` |
| `context/ux-patterns.md` | 0 · B-1 · B-3 | 문제 구조 → 화면 패턴 매핑, 축 후보 | `PT-nn` / `AX-nn` |
| `context/mockup-board.md` | B-3.5 | Figma 이전에 HTML 목업 3안으로 사람의 선택을 받는 자리의 형식·실패 조건 | `MB-nn` |
| `context/visual-criteria.md` | C | 봐야 아는 것의 판별 기준 | `VC-nn` |
| `context/usability-heuristics.md` | A · C | 사용성 하한선 (닐슨 10원칙). 규칙마다 판정 매체 `노드`/`화면`/`플로우` 명시 | `UH-nn` |
| `context/ai-slop.md` | 0 · B-3 · B-4 · A · C | AI 슬롭 53항목과 게이트별 배치. 판정식·`escape`·`cause` 라우팅 | 점 표기 id (`color.purple-blue-gradient`) |
| `context/design-system-doc.md` | B-4 · A · C | `DESIGN.md` 산출물의 형식·근거 요건, 모바일 고정 제약 | `DS-nn` |

- **기준값은 `context/`에 하드코딩하지 않는다.** 팔레트·터치 타깃 같은 프로젝트 값은 **`DESIGN.md`**(B-4 산출물)에서 주입받고, `context/`는 *무엇을 어떻게 보는가*만 담는다 (판단기준 3계층 중 "항목 고정, 값은 프로젝트별").
- **값은 `DESIGN.md`, 방향은 `brief.md`.** "뉴트럴은 웜 계열"은 0단계가 반응에서 역추출한 **제약**이므로 `brief.md`, `#F7F5F2`는 B단계가 그 제약 안에서 고른 **해**이므로 `DESIGN.md`다. 같은 값을 두 파일에 쓰지 않는다 — 갈라지는 순간 어느 쪽으로 판정할지 정할 수 없다.
- **`context/`(하네스 내장 지식)와 `references.md`(B-2가 이번 프로젝트에서 소싱한 결과)는 다른 물건이다.** 전자는 프로젝트를 넘어 누적되고, 후자는 프로젝트와 함께 버려진다.
- **모든 판정·후보에 규칙 ID를 인용한다.** ID 없는 지적은 리포트에 쓰지 않는다. 어느 규칙이 실제로 발동했는지가 곧 그 규칙의 품질 데이터다.
- **예외 1개** — `ai-slop.md`만 기준값을 하드코딩한다. 거기 박힌 hex·hue·비율은 프로젝트가 지켜야 할 값이 아니라 **AI 기본값의 지문(금지값)**이고, `DESIGN.md`의 토큰에 근거와 함께 등재됐거나 `brief.md`의 "안티슬롭 제약"에서 명시적으로 허용됐으면 발동하지 않는다. 이유는 그 문서 §2에.

## AI 슬롭 게이트

슬롭 검사는 5번째 단계가 아니라 **0/B/A/C에 나눠 붙는 필터**다. 전수 검사를 마지막에 몰아서 하면
제일 비싼 방법으로 제일 늦게 잡는다.

- **`SL0`(4) = B-4 예방 / `SL-A`(38) = A단계 노드 검출 / `SL-C`(11) = C단계 스크린샷 검출.**
- **`SL0`의 "0"은 단계 번호가 아니라 *화면이 0장일 때*라는 뜻이다.** 이 4항목이 검사하는 것(팔레트·서체·UI 킷 기본값·막연한 취향어)은 전부 **B단계가 고른 해**이므로, 값이 아직 없는 0단계에서는 판정 자체가 성립하지 않는다. 그래서 판정 시점은 `DESIGN.md`가 완성된 B-4 종료 직후다. **여전히 Figma에 아무것도 그리기 전이므로 "예방이 검출보다 싸다"는 원래 이점은 그대로다.**
- 0단계 종료 시에는 슬롭 id를 확정하지 않고 **전제조건만 검사한다** — `brief.md`의 "안티슬롭 제약"이 비어 있거나 역추출한 판단기준이 라벨 단어뿐이면 B단계로 넘어가지 않는다. 여기서 막히는 것은 `SL0`의 `underspec` 계열이 나중에 B-4에서 터질 것을 미리 막는 것이다.
- **`SC`와 혼동하지 않는다.** 이 하네스에서 `SC`는 A단계 구조 체크다. 슬롭 게이트는 `SL` 접두사를 쓴다.
- 항목의 근거는 `context/ai-slop.md`의 세 표뿐이다. **거기 없는 id를 짓지 않는다.** 프로젝트별 클리셰는 `references.md`의 "클리셰 후보"로 따로 관리한다.
- **기본은 리포트 전용.** 사용자가 "고쳐줘"라고 명시할 때만 수정한다.
- 지적에는 항상 `escape`(대체 패턴)를 함께 준다. **"빼라"만 하는 지적은 금지.**
- 라우팅은 항목의 `cause` 태그가 이미 정해 놓았다 — 판정 시점에 즉흥으로 정하지 않는다.

## 0단계 — 요구사항 정렬

무엇을 만들어야 하는지 자체가 불확실할 때, 화면을 만들기 **전에** 실행한다.

**B단계와의 경계** — 둘 다 "여러 개를 보여주고 반응을 받는다"로 읽히므로 한 줄로 못박는다.

> **0단계 산출 = 제약(후보 공간을 좁히는 규칙). B단계 산출 = 해(그 안에서 고른 후보).**
> 0단계의 자극은 반응을 끌어내려고 만들었다 버리는 것이고, B단계의 후보는 채택하려고 만드는 자산이다.

**예산**: 전체 45분 / 자극 라운드 최대 2회 / 라운드당 결정 지점 5개 이하.
**역할 규칙**: 반응을 주는 사람은 클라이언트 대리이며 **라벨을 말하지 않는다.** 라벨은 하네스만 붙인다.

### 1막 — 읽기 (10분, 사람 개입 0)

**시작 전 `context/ux-patterns.md`를 Read한다.** 문제 구조를 `PT-nn`에 대보면 결정 지점이 훨씬 빨리 드러난다.

요구사항 문서만 읽고 아래 다섯을 뽑아 `core-problem.md`에 쓴다 (템플릿: `templates/core-problem.md`).

1. **핵심 사용자 1명** — 부하를 지는 역할을 고른다. 조회만 하는 역할, 작업량이 1회인 역할은 탈락.
2. **핵심 문제 1개** — 기존 대안이 왜 실패하는지를 설명하지 못하면 문제 정의가 아니다.
3. **설계 제약 `D-nn`** — 핵심 문제에서 파생된 것만. 일반 UX 원칙(되돌리기·접근성)은 쓰지 않는다. 그건 A/C단계가 잡는다.
4. **결정 지점 `DP-nn`** — 하네스가 혼자 못 정하는 갈림길을 열거하고 `사람 판단 필요` / `기본값으로 가정` 둘로 나눈다. **전자만 2막의 자극이 된다.**
5. **가정 로그 `ASSUMP-nn`** — 뒤집혔을 때의 영향까지 함께 적는다.

두 개의 강제 규칙:

- **판별력 테스트** — 각 줄 옆에 *"이 줄이 반대였다면 어떤 화면 결정이 뒤집히는가"*를 답할 수 없으면 지운다. 이름·나이·성격 형용사·"~를 선호함"은 전부 탈락한다. 통과하는 것은 **숫자 / 빈도 / 맥락 / 실패 비용 / 역할 비대칭** 다섯 종류뿐이다.
- **근거 추적** — 모든 줄에 요구사항 문서의 근거를 단다. 없으면 삭제하거나 `ASSUMP-nn`으로 강등한다. "이 정도는 상식이니까"로 넣기 시작하면 하네스가 요구사항이 아니라 **자기가 지어낸 인물**을 근거로 화면을 만든다.

> `core-problem.md`는 **사람에게 보여주는 물건이 아니다.** "이 페르소나 맞나요?"라고 승인받는 순간 라벨형 질문으로 회귀한다. 사람이 만나는 것은 여기서 파생된 자극이고, 검증은 간접적으로 일어난다 — "이 사람 이렇게 안 할 것 같은데요"라는 반응이 페르소나 수정 신호다.

### 2막 — 자극 (25분)

- **자극은 외부에서 소싱하지 않고 하네스가 직접 생성한다.** 소싱 비용이 0이고, 남의 앱 스크린샷보다 *이 요구사항의 실제 화면*을 거칠게 그린 쪽이 반응을 훨씬 정확하게 끌어낸다.
- **매체**: Artifact로 자극 보드를 퍼블리시하고 링크를 사람에게 준다. 폴백은 로컬 HTML 파일을 브라우저로 여는 것. 터미널은 사람에게 화면을 보여줄 수 없으므로 매체를 정하지 않으면 이 단계는 실행 불가다.
- **형식**: 결정 지점 하나당 선택지를 **클릭 가능한 로우파이** 또는 **시나리오 내러티브**로 만든다. 다이어그램 금지(또 다른 전문 표기법이라 라벨형 질문과 같은 함정), 라벨형 질문 금지.
- **받는 것**: "좋다 / 싫다 + 왜"의 자유서술. **원문 그대로** `brief.md`에 보존한다. 요약하면 역추출 근거가 사라진다.
- **소싱 방법**: TODO — 이 도메인에서 자극을 무엇으로 만들지 (도메인마다 다름)

**클라이언트가 없을 때 (폴백)** — 반응을 줄 사람을 구할 수 없으면 2막을 건너뛰지 말고 아래로 대체한다.

> 요구사항 문서의 **상황 서술 문장 하나하나를 "반응"으로 간주해** 역추출한다.
> "평균 40~60명, 많으면 100명"은 이미 하나의 반응이고, 여기서 *카드 그리드는 스크롤 지옥이 되므로
> 고밀도 리스트가 기본이어야 한다*는 제약이 나온다. 문장 → 제약을 표로 만들어 `brief.md`에 남긴다.

이 대체는 **약하다.** 요구사항 문서가 말하지 않은 것은 끝내 드러나지 않으므로, 나온 제약은 전부
`ASSUMP-nn`을 달고 3막의 가정 로그로 간다. 사람을 구할 수 있으면 반드시 원래 절차를 쓴다.

### 3막 — 역추출 (10분)

- 반응 원문을 **제약으로 번역**한다. TODO — 역추출 예시 1~2개 (예: "산만하다" → "정보밀도 낮게 선호")
- 확정 안 된 정보는 침묵 처리하지 않고 `ASSUMP-nn`으로 명시한다.
- `brief.md` 스키마를 채운다. **빈 칸이 다음 질문을 결정한다.**
- **종료 조건**: 시간이 아니라 산출물 기준 — `brief.md`의 필수 필드가 전부 `값 또는 ASSUMP-nn`으로 채워지면 종료. 빈 칸이 남아 있고 라운드 상한에 도달하면 그 칸을 가정으로 강등하고 넘어간다.

### 산출물과 하류 계약

`core-problem.md`(문제 정의) + `brief.md`(반응 원문·역추출한 방향성 제약·안티슬롭 제약·모바일 사용 맥락).

**토큰 값은 여기서 나오지 않는다.** 팔레트·서체·간격은 B-4의 `DESIGN.md`가 정본이다 — 0단계에서 값을 확정하면 B-1의 비주얼 무드 축이 시작부터 죽는다.

> 페르소나를 여러 명 늘어놓는 것은 1막의 **중간 작업**이지 하류가 참조하는 산출물이 아니다. B단계가 실제로 읽는 것은 **핵심 사용자 1명**이므로, 후보를 벌려보는 절차까지 `core-problem.md §1` 안에 두고 별도 파일을 만들지 않는다.

다음 단계는 이렇게 참조한다.

- **B단계 축 식별** — 축 후보는 `DP-nn`에서만 뽑는다. DP가 아닌 것을 축으로 세우면 이미 정해진 것을 다시 흔드는 것이다.
- **B단계 후보 필터** — `D-nn`을 위반하는 후보는 비교 대상에서 제외하고, 제외 사유를 `decisions.md`에 남긴다.
- **B-4 · A단계** — 체크 기준값(팔레트·간격·터치 타깃·네이밍)은 `brief.md`가 아니라 **`DESIGN.md`**에서 가져온다. 0단계가 넘기는 것은 그 값을 고를 때 지켜야 할 **방향성 제약**과 `mobile.platform`을 가르는 사용 맥락이다.
- **0단계 종료 전제조건 검사** — 3막 종료 시 둘을 확인한다. 슬롭 id를 확정하는 자리가 아니다(값이 아직 없으므로 판정 불가). ① `brief.md`의 "안티슬롭 제약"에 금지 id와 그 **근거 반응 원문**이 있는가 ② 역추출한 판단기준이 라벨 단어("모던·깔끔·프리미엄")만이 아니라 레퍼런스 또는 수치를 동반하는가. 둘 중 하나라도 아니면 B단계로 넘어가지 않는다 — 넘어가봐야 B-4의 `SL0`에서 `underspec`으로 되돌아온다.
- **C단계 반복 실패 → 0단계 에스컬레이션** — 돌아와서 할 일은 재질문이 아니라, `core-problem.md`의 **반증 조건**과 **가정 로그**를 점검하는 것이다. **어느 `ASSUMP-nn`이 틀렸는지 지목하는 것**이 이 에스컬레이션의 실질이다. 가정에 ID가 없으면 돌아와도 무엇을 다시 물을지 알 수 없다.

## B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.
**B-1 → B-2 → B-3 → B-3.5 → B-4 순서를 지킨다.** 축보다 레퍼런스를 먼저 보면 축이 레퍼런스에 맞춰 왜곡된다(앵커링).
B-3.5는 후보를 사람이 볼 수 있는 형태로 내려앉혀 선택을 받는 자리이므로 후보 없이 먼저 열 수 없고,
B-4는 그 선택까지 값으로 고정하는 자리이므로 앞 넷 없이 먼저 쓸 수 없다.

### B-2. 레퍼런스 소싱

0단계의 레퍼런스와 목적이 다르다. **0단계 = 사람에게 줄 자극**(취향 역추출), **B-2 = 에이전트가 쓸 재료**(메커니즘 조달).

**시작 전 `context/reference-channels.md`를 Read한다.** 채널 목록·선택 규칙·고유 사용법은 전부 거기 있고, 여기에는 채널이 뭐든 변하지 않는 것만 둔다.

**소싱은 채널에 종속되지 않는다.** 아래 요건이 본체이고 채널(`CH-nn`)은 요건을 채우려고 갈아끼우는 어댑터다. 특정 채널이 죽거나 유료화돼도 B-2는 그대로 굴러가야 한다.

1. 이번 축에서 **무엇을 알아야 하는지**를 먼저 정한다 → `reference-channels.md`의 "필요 → 채널" 표로 채널을 고른다. 못 보는 채널을 아무리 뒤져도 안 나온다(예: 빈 상태 처리를 큐레이션 갤러리에서 찾는 것).
2. **축당 서로 다른 출처 2개 이상, 그중 최소 1개는 다른 도메인.** 자도메인은 컨벤션 추출용, 타도메인이 후보 생성의 진짜 재료다. 동일 카테고리만 보면 그 카테고리의 클리셰를 그대로 재생산하게 되고, 그건 `VC-06`·`SL-C`에서 탈락할 물건을 B단계에서 만드는 꼴이다.
3. **축당 채널 2종 이상을 권장한다.** 한 축의 레퍼런스가 전부 한 채널에서 오면 그 채널의 사각지대를 그대로 상속한다.
4. 수확물은 채널과 무관하게 **메커니즘 카드 한 포맷**으로 환원한다(해결한 문제 / 메커니즘 / 이식 가능성 / 안 가져올 것). "예쁘다"밖에 안 나오면 채널이 잘못됐거나 잘못 본 것이다.
5. 카드마다 **출처 URL과 채널 ID(`CH-nn`)를 기록한다.** C단계에서 근거로 재소환되고, 재발산(C 라우팅 2번) 때 중복 소싱을 막는다.
6. 접근이 막힌 채널(로그인·유료 벽)은 **사람에게 요청한다.** 우회하지 않는다.

**병렬 실행**: 축마다 서브에이전트 1개. 각 에이전트는 **자기 축 하나만 보고 나머지 축은 명시적으로 무시**시킨다 — 안 그러면 "예쁜 화면" 한 장이 여러 축에 동시에 영향을 줘서 축 분리가 소싱 단계에서 이미 깨진다.

**기록**: 레퍼런스를 통째로 저장하지 않고 축 단위로 해체해 `references.md`의 메커니즘 카드로 남긴다. 캡처는 `refs/`에.

**채널 갱신(누적)**: 새 채널을 쓰거나 기존 채널에서 기대한 게 안 나왔으면 `context/reference-channels.md`의 `CH-nn` 사각지대를 갱신한다. 실제로 안 나온 것이 곧 사각지대다.

### B-3. 후보 생성·수렴

- **후보 시드**: `context/ux-patterns.md`의 `PT-nn` 중 이 축의 문제 구조에 걸리는 것을 먼저 올린다. 각 PT의 *성립 조건·무너지는 조건*을 이 프로젝트 숫자(core-problem.md §1의 규모·빈도)에 대입해 걸러낸다 — 조건에 안 맞는 패턴은 후보가 아니다.
- **후보 생성 방식**: 축마다 **후보 3개**를 병렬 생성한다(서브에이전트 1개당 축 1개, B-2와 같은 분업). 셋은 취향이 아니라 **위험도 축** 위에 놓는다 — 컨벤션 그대로 / 수렴 결과 / 타도메인 메커니즘을 더 민 것. 이 셋이 그대로 B-3.5 목업 보드의 3안이 되므로 여기서 벌어지지 않으면 목업에서도 안 벌어진다.
- **후보 생성 지시문에 `brief.md`의 금지 슬롭 id와 그 `escape` 패턴을 넣는다.** 후보를 만드는 시점이 `median` 계열 슬롭을 막을 수 있는 유일한 자리다.
- **축 분리 실패 신호**: 한 축의 후보들이 **같은 슬롭 id를 공유하면 그 축은 분리에 실패한 것이다.** 축을 다시 나눈다. 후보 3개가 전부 중앙정렬 히어로라면 그건 "무드" 축이 아니라 색만 바꾼 것이다. (아래 "베끼기 방지"와 짝을 이루는 규칙 — 하나는 레퍼런스에 붙은 것을, 하나는 중앙값에 붙은 것을 잡는다.)
- **베끼기 방지**: 후보 하나가 레퍼런스 하나에 1:1 대응하면 실패 신호다. 후보는 축 위의 좌표이지 레퍼런스의 복제가 아니다. 최소 2개 레퍼런스의 메커니즘이 섞이거나, 메커니즘을 우리 제약에 맞게 변형한 흔적이 있어야 한다.
- **비교·수렴 방식**: 후보를 만든 에이전트가 아닌 **두 관점으로 교차 비평**한다. ① **`P1` 관점** — `core-problem.md §1`의 규모·빈도를 실제로 대입해 그 횟수만큼 반복했을 때 견디는가(`UH-07`) ② **하류 이식 관점** — 이 후보가 `DESIGN.md`의 토큰과 Figma Variant로 내려앉을 때 상태가 몇 개로 늘어나는가. 두 관점의 결론이 갈리면 그 자체를 `decisions.md`의 "남은 트레이드오프"에 적고, 갈린 채로 B-3.5 목업 보드에 올려 사람에게 넘긴다.
- **선택 이유를 비워두지 않는다.** 축별 "선택 이유"가 비면 A단계에서 `meta.mean-best-aesthetic`(strong)이 확정된다. 결정을 안 한 것이 곧 슬롭이기 때문이다.
- **수렴 게이트**: 선택한 후보마다 *"이 선택은 어느 레퍼런스의 어떤 메커니즘에서 왔고, 그 메커니즘이 우리 페르소나에서도 성립하는 이유는?"* 에 답한다. 답이 안 나오면 근거 없는 선택으로 보고 반려한다. `decisions.md`의 `근거 ref` 열에 기록.
- **승격(누적)**: B-2에서 새로 발견한 메커니즘이 *다음 프로젝트에서도 쓰일 패턴*이면 `context/ux-patterns.md`에 `PT-nn`으로 승격해 5필드로 기록한다. 이번 프로젝트에서만 유효한 것은 `references.md`에 두고 승격하지 않는다. 이 승격이 하네스가 프로젝트를 거치며 좋아지는 유일한 경로다.
- **산출물**: `references.md` (템플릿: `templates/references.md`), `decisions.md` (템플릿: `templates/decisions.md`). 후보 표에 출처 `PT-nn`을 인용한다.

### B-3.5. 목업 보드 — 사람의 선택 (Figma 이전)

**시작 전 `context/mockup-board.md`를 Read한다.** 형식·실패 조건은 전부 `MB-01`~`MB-06`에 있다.

B-3의 수렴은 **표에서** 끝난다. 사람은 표로 화면을 고르지 못하고, `DESIGN.md`와 Figma는
되돌리는 비용이 크다. 그래서 **가장 싼 자리에서 사람의 선택을 한 번 받는다.**

- **매체는 HTML이다.** `work/<프로젝트>/mockups/`에 로컬 HTML 한 장으로 만들고 브라우저로 연다.
  Figma가 아닌 이유는 이 단계가 Figma **이전**이기 때문이다 — 여기서 Figma를 쓰면 되돌리는 비용이
  이 단계가 아끼려던 것과 같아진다.
- **정확히 3안**: **1. 추천안**(B-3 수렴 결과) / **2. 무난함**(자도메인 컨벤션 그대로) /
  **3. 도전·과감**(타도메인 메커니즘을 더 민 것). 셋을 가르는 것은 취향이 아니라 **위험도**다 (`MB-01`).
- **3안은 같은 화면·같은 더미 데이터로 그린다** (`MB-02`). 데이터에는 `core-problem.md §2`의
  까다로운 경우(중복 소속·무응답·충돌 등)를 **실물로 심는다** — 없으면 3안이 전부 합격으로 보인다.
- **색·서체는 가설이다.** `DESIGN.md`가 아직 없으므로 그 사실을 화면에 명시한다 (`MB-04`).
  단 비주얼 무드가 축이라면 3안에서 갈라져야 한다 — 같게 그리면 그 축은 사람의 선택을 못 받는다.
- **받는 것은 번호가 아니라 "어디가 왜"다** (`MB-05`). 부분 채택("1안인데 리스트는 3안처럼")을
  열어두고, 받은 말을 **원문 그대로** `decisions.md`에 남긴다. 침묵을 합의로 읽지 않는다.
- **보여주기 전 실패 조건 4개를 검사한다** (`mockup-board.md` 말미). 3안이 같은 슬롭 id를
  공유하면 축이 안 벌어진 것이므로 보여주지 않고 B-3으로 돌아간다.
- **목업은 산출물이 아니다** (`MB-06`). Figma로 그대로 옮기지 않는다 — 선택된 안은 B-4를 거쳐
  값이 된 뒤에 그려진다. 목업과 `DESIGN.md`가 어긋나면 언제나 `DESIGN.md`가 이긴다.

### B-4. 디자인 시스템 문서 고정

**시작 전 `context/design-system-doc.md`를 Read한다.** 작성 규칙(`DS-01`~`DS-07`)은 전부 거기 있다.

수렴이 끝났으면 **Figma에 무엇도 그리기 전에** 축별 선택을 실제 값으로 내려앉힌다.
산출물은 `DESIGN.md` (템플릿: `templates/DESIGN.md`, 포맷: [google-labs-code/design.md](https://github.com/google-labs-code/design.md)).
YAML front matter가 토큰 값, 마크다운 본문이 그 값의 근거다 — **산문이 본체이고 토큰은 산문이 참조하는 맥락이다.**

- 이 문서가 **모든 디자인 토큰 값의 정본**이다. `brief.md`에는 방향성 제약만 남고 값은 여기 있다. 두 곳에 같은 값을 쓰지 않는다.
- `mobile:` 블록 여섯 값은 비워둘 수 없다(`DS-07`). 값의 근거는 `CH-04`(Apple HIG / Material)에서 가져와 `## Layout` 산문에 인용한다.
- `## Overview`의 첫 문단은 **한 손에 쥔 구체적인 물건 하나**를 지목한다(`DS-02`). 형용사 나열은 그 자체로 `meta.vague-taste-word-prompting`(strong) 확정이다. 이 문장은 `references.md`의 메커니즘 카드에서만 나오므로, **B-2를 건너뛴 프로젝트는 여기서 막힌다.**
- `## Do's and Don'ts`는 발명하지 않는다(`DS-03`) — `references.md`의 클리셰 후보와 `brief.md`의 금지 슬롭 id에서만 가져온다. 10줄을 넘으면 Overview가 부실하다는 신호다.
- `components`에는 **B-3.5에서 선택된 화면에 실제로 등장한 것만** 적는다(`DS-06`). 라이브러리를 미리 설계하지 않는다 — 화면에 안 나온 컴포넌트는 어느 화면도 검증하지 않은 추측이다. **상태 엔트리(`-pressed`/`-disabled`/`-loading`/`-empty`)의 정본은 이 문서다** — Figma에 variant로 만들지 않으므로, 여기 적히지 않은 상태는 어디에도 존재하지 않게 된다. **모바일에는 hover가 없다 — 그 자리에 `-pressed`를 놓는다.**
- 축마다 어느 섹션에 내려앉았는지를 `decisions.md`에 표로 남긴다(`DS-04`). 어느 섹션에도 안 걸리는 축은 화면에 영향을 주지 못한 축이다.

**`SL0` 게이트 (여기서 실행)** — `DESIGN.md`를 다 쓰면 `context/ai-slop.md`의 `SL0` 표 4항목으로
이 문서 자체를 검사한다. **화면이 아직 0장이므로 제일 싼 자리에서 잡는다.** `strong`이 하나라도
확정되면 Figma로 넘어가지 않는다. 토큰 자기정합성(`DS-05`: 깨진 참조 / 고아 토큰 / 단계 수 하한)도
같이 본다 — 외부 린터를 쓰지 않으므로 하네스가 직접 대조한다.

**재작성** — C단계 실패로 B에 회귀해 후보를 바꿨으면 `DESIGN-v2.md`로 새로 쓰고 원본을 덮어쓰지 않는다.
무엇이 바뀌었는지가 남지 않으면 "후보를 바꿔도 같은 슬롭이 3회 재발"을 셀 수 없다.

### B-2가 후속 단계에 넘기는 것

레퍼런스를 그냥 참고자료로 끝내지 않기 위한 연결이다.

- 레퍼런스에서 실측한 수치(간격, 여백, 화면당 정보 개수, **터치 타깃 실측 높이**, 본문 크기) → **B-4에서 `DESIGN.md`의 토큰 값과 `harness.scaleFloor`로 내려앉는다.** radius·spacing·글자 크기는 *값*만이 아니라 **종류 수**도 실측한다 — 종류 수가 곧 위계다
- `references.md`의 클리셰 후보 목록 → **B-4에서 `DESIGN.md`의 `## Do's and Don'ts`로 승격**되고, C단계가 그 목록을 `VC-06`의 판정 항목으로 소환한다. 목록이 비면 `VC-06`은 `판정 불가`다 (AI 일반 슬롭은 `SL-C`가 따로 본다)
- 컨벤션 목록 → 후보 생성 시 지켜야 할 하한선

## Figma 실행 — 최종 화면만 그린다

`DESIGN.md`가 통과했으면 여기서 처음으로 Figma를 연다. 입력은 둘이다 — **B-3.5에서 선택된 안**과
**`DESIGN.md`의 값**. 이 절은 판단 기준이 아니라 **순서와 예산**이므로 `context/`가 아니라 여기 있다.

> **디자인은 `DESIGN.md`에서 이미 끝났다. Figma는 그 결과를 화면 한 벌로 실체화하는 자리다.**
> **컴포넌트 라이브러리도, variant 세트도 Figma에 만들지 않는다. 그리는 것은 최종 화면뿐이다.**

이유는 둘이다. ① 화면보다 먼저 만든 컴포넌트는 어느 화면도 검증하지 않은 추측이고, 쓰이지도 않는
variant가 A단계의 `componentReuseFloor`를 **형식적으로만** 통과시킨다. ② Figma MCP 호출은 이 하네스에서
제일 비싼 자원이다. 컴포넌트·variant를 만드는 왕복은 화면 품질에 아무것도 더하지 않으면서 예산만 태운다.

### 호출 예산

| 자리 | 호출 | 상한 |
|---|---|---|
| 화면 작성 | `use_figma` 쓰기 | **1회** (화면 전부를 한 번에 만든다. 프레임마다 나눠 부르지 않는다) |
| A단계 | 노드 덤프 읽기 | **1회** — `SC` 9개와 `SL-A` 38개를 **같은 덤프 한 벌로** 판정한다 |
| C단계 | 스크린샷 렌더 | **1회** — 밀집 영역 3배 크롭은 받은 이미지를 **로컬에서** 잘라 쓴다. 다시 렌더하지 않는다 |
| 수정 재검 | 쓰기 + 재판정 | 게이트당 3회 상한을 그대로 따른다 (A·C 공통 라우팅) |

**상한을 넘겨야 할 것 같으면 화면을 더 부르기 전에 `DESIGN.md`를 의심한다.** 왕복이 늘어나는 건
대개 값이 문서에 없어서 Figma에서 즉흥으로 정하고 있다는 신호다.

### 그리는 것 / 안 그리는 것

- **그린다** — 선택된 안의 핵심 화면(1~2장)과, **사용자가 실제로 보는 상태 화면**(빈 상태·로딩·에러).
  후자는 C단계 `UH`·`VC-07`이 화면 없이는 `판정 불가`가 되므로 필요한 것만 프레임으로 만든다.
- **안 그린다** — 컴포넌트 마스터, variant 세트, 사용처 없는 스타일·variable, 화면에 안 쓰인 토큰.
  `-pressed`/`-disabled`처럼 **정지 화면으로 확인할 수 없는 상태**는 Figma에 만들지 않는다.
  그 상태의 정본은 `DESIGN.md`의 `components` 엔트리이고, 검증 매체도 노드가 아니라 그 문서다.
- 화면은 `DESIGN.md`의 토큰 값을 그대로 쓴다. 로컬 스타일과 즉흥 값은 쓰지 않는다.
  **그리다 새 값이 필요해지면** `DESIGN.md`에 근거 한 줄과 함께 추가한 뒤 쓴다. 화면과 문서가
  어긋나면 언제나 `DESIGN.md`가 이긴다.
- **목업을 스크린샷 떠서 따라 그리지 않는다** (`MB-06`). 옮기는 것은 목업의 픽셀이 아니라 선택된 **구조**다.
- **도구**: `use_figma` 호출 전에 `figma-use` 스킬을 Read한다. 화면 단위 작업이므로
  `figma-generate-design`이 맞는 경로이고, 라이브러리 선행 생성(`figma-generate-library`)은
  이 하네스에서 쓰지 않는다 — 만들지 않기로 한 것을 만드는 스킬이다.

### 레이어 위생 — 컴포넌트가 없어도 A단계는 판정된다

컴포넌트를 안 만든다고 노드가 엉망이어도 되는 건 아니다. A단계가 보는 것은 마스터의 존재가 아니라
**같은 역할의 노드가 같은 값으로 그려졌는가**이므로, 화면을 그릴 때 이것만 지키면 된다.

- 반복 요소(리스트 로우·카드·버튼)는 **한 벌을 그려 복제**한다. 복제본끼리 패딩·높이·타이포가
  달라지면 그것이 곧 A단계 불합격이다.
- 레이어 이름은 `harness.layerNamingConvention`을 따라 붙인다 — 컴포넌트가 없으므로 이름이
  역할을 식별하는 **유일한 단서**다. `Frame 427`이 남아 있으면 A단계가 무엇이 반복인지 알 수 없다.

## A단계 — 구조적 사실 검증

화면이 다 만들어진 뒤, 데이터로 예/아니오 또는 수치로 검증한다. 스크린샷 없이 Figma 노드 속성만으로 확인 가능.

**시작 전 `context/ai-slop.md`와 `DESIGN.md`를 Read한다.** 아래 `SC` 9개와 `SL-A` 38개는 **같은 노드 덤프 한 벌로** 판정한다.

체크 카테고리 `SC` (항목은 고정, **기준값은 전부 `DESIGN.md`에서 읽는다**. 해당 값이 TODO면 그 체크는 `판정 불가`):

- [ ] 컬러 팔레트 일관성 — 기준: `DESIGN.md` front matter의 `colors` 전체. 여기 없는 색이 노드에 있으면 불합격
- [ ] 타이포 스타일 재사용 — 기준: `typography` 엔트리. 정의 밖의 크기·굵기가 쓰였는가
- [ ] Spacing 그리드 준수 — 기준: `spacing` 값과 `harness.scaleFloor.spacing`
- [ ] 반복 요소 일관성 — 기준: `harness.componentReuseFloor`. **Figma 컴포넌트를 만들지 않으므로 인스턴스 비율로 세지 않는다.** 같은 역할의 반복 노드(리스트 로우·카드·버튼)가 패딩·높이·타이포·색을 **같은 값으로** 쓰는 비율을 본다
- [ ] 레이어 네이밍 semantic 여부 — 기준: `harness.layerNamingConvention`
- [ ] 상태 커버리지 — 기준: `harness.variantCoverage` = `components`의 상태 엔트리 목록(`DS-06`). 판정은 두 갈래다: **사용자가 보는 상태**(`-empty`/`-loading`/에러)는 **화면 프레임이 존재하는가**로, `-pressed`/`-disabled`처럼 정지 화면으로 확인 불가한 상태는 **`DESIGN.md`에 값이 선언됐는가**로 본다. Figma variant를 찾지 않는다. **모바일이므로 hover가 아니라 `-pressed`다**
- [ ] **모바일 — 터치 타깃** — 인터랙티브 노드의 히트 영역이 `mobile.minTouchTarget` 이상인가. 시각적 크기가 작은 건 괜찮지만 히트 영역은 안 된다
- [ ] **모바일 — 세이프 에어리어** — `mobile.safeAreaTop`/`safeAreaBottom` 대역에 조작 요소가 침범했는가. 하단 고정 CTA가 대표적 위반이다
- [ ] **모바일 — 프레임 폭** — 프레임이 `mobile.designViewportWidth`인가, 그리고 `mobile.minViewportWidth`에서 가로 스크롤이나 잘림이 생기는가 (노드 x좌표+폭으로 계산 가능하므로 눈이 필요 없다)
- [ ] **`SL-A` 슬롭 검출 (38항목)** — `context/ai-slop.md`의 `SL-A` 표. **위 9개와 같은 노드 덤프를 재사용하고 다시 조회하지 않는다.**
      순서(싼 것부터): 텍스트(11) → 색·폰트(10) → 구조(16) → 누적(1)
      `brief.md`의 `산출물 유형`으로 `랜딩` 전용 항목을 먼저 걸러 `미적용` 처리한다.
      **`strong` 1건이면 실패. `weak`은 같은 프레임에 2건 이상이면 `strong`으로 승격.**

판정 리포트는 `VC`·`UH`와 같은 형식으로 쓴다. `판정 불가`를 합격으로 처리하지 않고, `미적용`(그 산출물에 개념 자체가 없음)과 구분한다.

### A·C 공통 — 실패 시 라우팅

**라우팅은 판정 시점에 즉흥으로 정하지 않는다.** `VC`는 규칙마다 박아둔 `라우팅` 필드를,
슬롭 항목은 `cause` 태그를 따른다. 규칙에 없으면 그 규칙이 미완성이다.

1. **국소적 결함** (표면 속성 하나의 문제) → 그 속성만 고쳐 **같은 게이트** 재검. B단계로 돌아가지 않는다.
2. **방향 자체가 틀림** (국소 조정으로 안 고쳐지는 구조적 문제) → B단계로 회귀, 다른 후보 선택 또는 재발산.
3. **반복 실패** (후보를 바꿔도 같은 이유로 계속 탈락) → 0단계로 에스컬레이션.

슬롭 항목의 `cause` → 위 번호 매핑:

| cause | 라우팅 |
|---|---|
| `no-verify` | ① 국소 |
| `median` / `no-constraint` | ② B단계 회귀 |
| `underspec` | ③ 0단계 에스컬레이션 |

- cause가 둘 이상이면 **더 상류로** 간다 (`underspec` > `median`/`no-constraint` > `no-verify`).
- `meta.`로 시작하는 슬롭 항목은 표면 수정으로 못 고친다. 무조건 ② 또는 ③이다.
- **재시도 상한: 게이트당 3회.** 초과하면 사람에게 에스컬레이션한다. 같은 슬롭 id가 후보를 바꿔도 3회 연속 나오면 상한과 무관하게 즉시 ③으로 간다(반복 실패 신호).
- 시도 회차와 재발 id는 `decisions.md` 말미의 "슬롭 게이트 상태"에 남긴다. 안 남기면 3회를 셀 수 없다.
- 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.

## C단계 — 미적·게슈탈트 판단

화면이 다 만들어진 뒤, 반드시 스크린샷을 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가.

**시작 전 `context/visual-criteria.md`·`context/usability-heuristics.md`·`context/ai-slop.md`와 이번 프로젝트의 `DESIGN.md`를 Read한다. 읽지 않고 판정하지 않는다.** 체크 항목의 실제 내용(증상·확인법·수정·라우팅)은 전부 거기에 `VC-nn`으로 있고, 이번 프로젝트가 스스로 금지한 것은 `DESIGN.md`의 `## Do's and Don'ts`에 있다.

**렌더는 `DESIGN.md`의 `mobile.designViewportWidth` 실제 크기로 한다.** 축소해서 보면 모바일 타이포와 터치 타깃 문제가 전부 사라진다. 여기에 `visual-criteria.md`의 밀집 영역 3배 크롭을 더하되, **크롭은 받은 이미지를 로컬에서 자른다 — 렌더를 다시 부르지 않는다**(Figma 실행 절의 호출 예산).

판정 리포트는 규칙 ID를 인용한 줄로만 쓴다:

```
[VC-01] 불합격 — 사이드바만 cool gray, 본문 카드는 warm cream. 라우팅: 국소
[VC-02] 합격
[VC-07] 판정 불가 — 빈 상태 화면이 렌더되지 않음
```

- "판정 불가"를 합격으로 처리하지 않는다. 볼 수 없으면 볼 수 있게 만든 뒤 다시 본다.
- **`SL-C` 슬롭 검출 (11항목)** — `context/ai-slop.md`의 `SL-C` 표. **`VC`·`UH`와 같은 스크린샷 한 장으로 함께 본다.** 렌더를 두 번 하지 않는다. 이미지가 없는 화면은 `img.*` 4항목을 `미적용`으로 건너뛴다. `meta.differentiation-failure`의 판정법은 **로고와 문구를 가려도 이 제품이라고 알아볼 근거가 남는가**다.
- **클리셰/AI슬롭의 일반 항목은 `SL-C`로 위임한다.** `VC-06`에는 **이번 프로젝트 항목**만 남기고, 그 목록은 `DESIGN.md`의 `## Do's and Don'ts`다(`references.md`의 클리셰 후보가 B-4에서 승격된 것). 같은 대상을 두 ID로 판정하면 리포트가 이중장부가 된다. **자기가 쓴 Don't를 자기가 어긴 것**이므로 라우팅은 대개 `방향`이다.
- `UH` 중 매체가 `플로우`인 규칙은 화면 1장으로 판정하지 않는다. **해당 상태 화면을 안 만들었다면 그 자체가 결함**이므로 `판정 불가`로 남기고 화면을 만든 뒤 다시 본다.
- `context/visual-criteria.md`로 안 잡히는데 실제로 눈에 거슬리는 것이 있으면, 고치고 끝내지 말고 **새 `VC`로 등재**한 뒤 판정한다.

### C단계 실패 시 라우팅

**A단계의 "A·C 공통 — 실패 시 라우팅" 절을 따른다.** 라우팅 3갈래·`cause` 매핑·재시도 상한(게이트당 3회)은
A단계와 C단계가 같은 규칙을 쓴다. C단계 고유 사항은 하나뿐이다 — `VC` 규칙의 `라우팅` 필드가
`cause` 태그와 같은 자리를 차지한다.

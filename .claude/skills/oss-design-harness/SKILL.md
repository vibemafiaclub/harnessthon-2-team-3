# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP(`use_figma`)로 실제 화면을 만드는 하네스.
**이 파일은 뼈대만 있는 빈 템플릿입니다.** 각 단계의 `TODO`를 채우는 것이 곧 이 스킬을 만드는 작업입니다.

순서를 그대로 따라가는 것이 아니라, 아래 4단계가 각각 무엇을 판단해야 하는지에 집중합니다.

## 참조 문서 (`context/`)

단계별 판단 기준은 이 파일이 아니라 `context/` 아래에 규칙 단위로 있다. **해당 단계 시작 전에 Read한다.**

| 파일 | 쓰는 단계 | 담는 것 | ID |
|---|---|---|---|
| `context/reference-channels.md` | 0 · B-2 | 레퍼런스를 어느 창구로 가져오는가, 채널별 사각지대 | `CH-nn` |
| `context/ux-patterns.md` | 0 · B-1 · B-3 | 문제 구조 → 화면 패턴 매핑, 축 후보 | `PT-nn` / `AX-nn` |
| `context/visual-criteria.md` | C | 봐야 아는 것의 판별 기준 | `VC-nn` |
| `context/usability-heuristics.md` | A · C | 사용성 하한선 (닐슨 10원칙). 규칙마다 판정 매체 `노드`/`화면`/`플로우` 명시 | `UH-nn` |

- **기준값은 `context/`에 하드코딩하지 않는다.** 팔레트·그리드 단위 같은 프로젝트 값은 `brief.md`에서 주입받고, `context/`는 *무엇을 어떻게 보는가*만 담는다 (판단기준 3계층 중 "항목 고정, 값은 프로젝트별").
- **`context/`(하네스 내장 지식)와 `references.md`(B-2가 이번 프로젝트에서 소싱한 결과)는 다른 물건이다.** 전자는 프로젝트를 넘어 누적되고, 후자는 프로젝트와 함께 버려진다.
- **모든 판정·후보에 규칙 ID를 인용한다.** ID 없는 지적은 리포트에 쓰지 않는다. 어느 규칙이 실제로 발동했는지가 곧 그 규칙의 품질 데이터다.

## 0단계 — 요구사항 정렬

무엇을 만들어야 하는지 자체가 불확실할 때, 화면을 만들기 **전에** 실행한다.

**B단계와의 경계** — 둘 다 "여러 개를 보여주고 반응을 받는다"로 읽히므로 한 줄로 못박는다.

> **0단계 산출 = 제약(후보 공간을 좁히는 규칙). B단계 산출 = 해(그 안에서 고른 후보).**
> 0단계의 자극은 반응을 끌어내려고 만들었다 버리는 것이고, B단계의 후보는 채택하려고 만드는 자산이다.

**예산**: 전체 45분 / 자극 라운드 최대 2회 / 라운드당 결정 지점 5개 이하.
**역할 규칙**: 반응을 주는 사람은 클라이언트 대리이며 **라벨을 말하지 않는다.** 라벨은 하네스만 붙인다.

### 1막 — 읽기 (10분, 사람 개입 0)

**시작 전 `context/ux-patterns.md`를 Read한다.** 문제 구조를 `PT-nn`에 대보면 결정 지점이 훨씬 빨리 드러난다.

요구사항 문서만 읽고 아래 다섯을 뽑아 `core-problem.md`에 쓴다 (템플릿: `templates/core-problem.md`).

1. **핵심 사용자 1명** — 부하를 지는 역할을 고른다. 조회만 하는 역할, 작업량이 1회인 역할은 탈락.
2. **핵심 문제 1개** — 기존 대안이 왜 실패하는지를 설명하지 못하면 문제 정의가 아니다.
3. **설계 제약 `D-nn`** — 핵심 문제에서 파생된 것만. 일반 UX 원칙(되돌리기·접근성)은 쓰지 않는다. 그건 A/C단계가 잡는다.
4. **결정 지점 `DP-nn`** — 하네스가 혼자 못 정하는 갈림길을 열거하고 `사람 판단 필요` / `기본값으로 가정` 둘로 나눈다. **전자만 2막의 자극이 된다.**
5. **가정 로그 `ASSUMP-nn`** — 뒤집혔을 때의 영향까지 함께 적는다.

두 개의 강제 규칙:

- **판별력 테스트** — 각 줄 옆에 *"이 줄이 반대였다면 어떤 화면 결정이 뒤집히는가"*를 답할 수 없으면 지운다. 이름·나이·성격 형용사·"~를 선호함"은 전부 탈락한다. 통과하는 것은 **숫자 / 빈도 / 맥락 / 실패 비용 / 역할 비대칭** 다섯 종류뿐이다.
- **근거 추적** — 모든 줄에 요구사항 문서의 근거를 단다. 없으면 삭제하거나 `ASSUMP-nn`으로 강등한다. "이 정도는 상식이니까"로 넣기 시작하면 하네스가 요구사항이 아니라 **자기가 지어낸 인물**을 근거로 화면을 만든다.

> `core-problem.md`는 **사람에게 보여주는 물건이 아니다.** "이 페르소나 맞나요?"라고 승인받는 순간 라벨형 질문으로 회귀한다. 사람이 만나는 것은 여기서 파생된 자극이고, 검증은 간접적으로 일어난다 — "이 사람 이렇게 안 할 것 같은데요"라는 반응이 페르소나 수정 신호다.

### 2막 — 자극 (25분)

- **자극은 외부에서 소싱하지 않고 하네스가 직접 생성한다.** 소싱 비용이 0이고, 남의 앱 스크린샷보다 *이 요구사항의 실제 화면*을 거칠게 그린 쪽이 반응을 훨씬 정확하게 끌어낸다.
- **매체**: Artifact로 자극 보드를 퍼블리시하고 링크를 사람에게 준다. 폴백은 로컬 HTML 파일을 브라우저로 여는 것. 터미널은 사람에게 화면을 보여줄 수 없으므로 매체를 정하지 않으면 이 단계는 실행 불가다.
- **형식**: 결정 지점 하나당 선택지를 **클릭 가능한 로우파이** 또는 **시나리오 내러티브**로 만든다. 다이어그램 금지(또 다른 전문 표기법이라 라벨형 질문과 같은 함정), 라벨형 질문 금지.
- **받는 것**: "좋다 / 싫다 + 왜"의 자유서술. **원문 그대로** `brief.md`에 보존한다. 요약하면 역추출 근거가 사라진다.
- **소싱 방법**: TODO — 이 도메인에서 자극을 무엇으로 만들지 (도메인마다 다름)

**클라이언트가 없을 때 (폴백)** — 반응을 줄 사람을 구할 수 없으면 2막을 건너뛰지 말고 아래로 대체한다.

> 요구사항 문서의 **상황 서술 문장 하나하나를 "반응"으로 간주해** 역추출한다.
> "평균 40~60명, 많으면 100명"은 이미 하나의 반응이고, 여기서 *카드 그리드는 스크롤 지옥이 되므로
> 고밀도 리스트가 기본이어야 한다*는 제약이 나온다. 문장 → 제약을 표로 만들어 `brief.md`에 남긴다.

이 대체는 **약하다.** 요구사항 문서가 말하지 않은 것은 끝내 드러나지 않으므로, 나온 제약은 전부
`ASSUMP-nn`을 달고 3막의 가정 로그로 간다. 사람을 구할 수 있으면 반드시 원래 절차를 쓴다.

### 3막 — 역추출 (10분)

- 반응 원문을 **제약으로 번역**한다. TODO — 역추출 예시 1~2개 (예: "산만하다" → "정보밀도 낮게 선호")

### 산출물과 하류 계약

`core-problem.md`(문제 정의) + `brief.md`(반응 원문·판단기준·토큰).

> 페르소나를 여러 명 늘어놓는 것은 1막의 **중간 작업**이지 하류가 참조하는 산출물이 아니다. B단계가 실제로 읽는 것은 **핵심 사용자 1명**이므로, 후보를 벌려보는 절차까지 `core-problem.md §1` 안에 두고 별도 파일을 만들지 않는다.

다음 단계는 이렇게 참조한다.

- **B단계 축 식별** — 축 후보는 `DP-nn`에서만 뽑는다. DP가 아닌 것을 축으로 세우면 이미 정해진 것을 다시 흔드는 것이다.
- **B단계 후보 필터** — `D-nn`을 위반하는 후보는 비교 대상에서 제외하고, 제외 사유를 `decisions.md`에 남긴다.
- **A단계** — 체크 기준값(그리드 단위·팔레트·네이밍)은 `brief.md`에서 가져온다.
- **C단계 반복 실패 → 0단계 에스컬레이션** — 돌아와서 할 일은 재질문이 아니라, `core-problem.md`의 **반증 조건**과 **가정 로그**를 점검하는 것이다. **어느 `ASSUMP-nn`이 틀렸는지 지목하는 것**이 이 에스컬레이션의 실질이다. 가정에 ID가 없으면 돌아와도 무엇을 다시 물을지 알 수 없다.

## B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.
**B-1 → B-2 → B-3 순서를 지킨다.** 축보다 레퍼런스를 먼저 보면 축이 레퍼런스에 맞춰 왜곡된다(앵커링).

### B-1. 독립 축 식별

**시작 전 `context/ux-patterns.md`를 Read한다.** 축 후보표(`AX-nn`)부터 검토하고, 거기 없는 축은 새로 뽑아 `AX`로 추가한다.

- TODO — 이 프로젝트에서 후보를 가를 독립적인 축이 무엇인지 (예: 비주얼 무드, 정보 밀도, UX 직관성 수준 — 예시일 뿐, 실제로는 프로젝트마다 다시 뽑아야 함)
- 축이 도저히 안 뽑히면 B-2를 소량(1쿼리)만 돌려 축 후보를 얻고 B-1로 돌아온다. 왕복은 1회까지.

### B-2. 레퍼런스 소싱

0단계의 레퍼런스와 목적이 다르다. **0단계 = 사람에게 줄 자극**(취향 역추출), **B-2 = 에이전트가 쓸 재료**(메커니즘 조달).

**시작 전 `context/reference-channels.md`를 Read한다.** 채널 목록·선택 규칙·고유 사용법은 전부 거기 있고, 여기에는 채널이 뭐든 변하지 않는 것만 둔다.

**소싱은 채널에 종속되지 않는다.** 아래 요건이 본체이고 채널(`CH-nn`)은 요건을 채우려고 갈아끼우는 어댑터다. 특정 채널이 죽거나 유료화돼도 B-2는 그대로 굴러가야 한다.

1. 이번 축에서 **무엇을 알아야 하는지**를 먼저 정한다 → `reference-channels.md`의 "필요 → 채널" 표로 채널을 고른다. 못 보는 채널을 아무리 뒤져도 안 나온다(예: 빈 상태 처리를 큐레이션 갤러리에서 찾는 것).
2. **축당 서로 다른 출처 2개 이상, 그중 최소 1개는 다른 도메인.** 자도메인은 컨벤션 추출용, 타도메인이 후보 생성의 진짜 재료다. 동일 카테고리만 보면 그 카테고리의 클리셰를 그대로 재생산하게 되고, 그건 C단계 AI슬롭 항목에서 탈락할 물건을 B단계에서 만드는 꼴이다.
3. **축당 채널 2종 이상을 권장한다.** 한 축의 레퍼런스가 전부 한 채널에서 오면 그 채널의 사각지대를 그대로 상속한다.
4. 수확물은 채널과 무관하게 **메커니즘 카드 한 포맷**으로 환원한다(해결한 문제 / 메커니즘 / 이식 가능성 / 안 가져올 것). "예쁘다"밖에 안 나오면 채널이 잘못됐거나 잘못 본 것이다.
5. 카드마다 **출처 URL과 채널 ID(`CH-nn`)를 기록한다.** C단계에서 근거로 재소환되고, 재발산(C 라우팅 2번) 때 중복 소싱을 막는다.
6. 접근이 막힌 채널(로그인·유료 벽)은 **사람에게 요청한다.** 우회하지 않는다.

**병렬 실행**: 축마다 서브에이전트 1개. 각 에이전트는 **자기 축 하나만 보고 나머지 축은 명시적으로 무시**시킨다 — 안 그러면 "예쁜 화면" 한 장이 여러 축에 동시에 영향을 줘서 축 분리가 소싱 단계에서 이미 깨진다.

**기록**: 레퍼런스를 통째로 저장하지 않고 축 단위로 해체해 `references.md`의 메커니즘 카드로 남긴다. 캡처는 `refs/`에.

**채널 갱신(누적)**: 새 채널을 쓰거나 기존 채널에서 기대한 게 안 나왔으면 `context/reference-channels.md`의 `CH-nn` 사각지대를 갱신한다. 실제로 안 나온 것이 곧 사각지대다.

### B-3. 후보 생성·수렴

- **후보 시드**: `context/ux-patterns.md`의 `PT-nn` 중 이 축의 문제 구조에 걸리는 것을 먼저 올린다. 각 PT의 *성립 조건·무너지는 조건*을 이 프로젝트 숫자(core-problem.md §1의 규모·빈도)에 대입해 걸러낸다 — 조건에 안 맞는 패턴은 후보가 아니다.
- **후보 생성 방식**: TODO — 축마다 후보 몇 개를 병렬 생성할지, 어떻게 생성할지
- **베끼기 방지**: 후보 하나가 레퍼런스 하나에 1:1 대응하면 실패 신호다. 후보는 축 위의 좌표이지 레퍼런스의 복제가 아니다. 최소 2개 레퍼런스의 메커니즘이 섞이거나, 메커니즘을 우리 제약에 맞게 변형한 흔적이 있어야 한다.

## C단계 — 미적·게슈탈트 판단

화면이 다 만들어진 뒤, 반드시 스크린샷을 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가.

**시작 전 `context/visual-criteria.md`와 `context/usability-heuristics.md`를 Read한다. 읽지 않고 판정하지 않는다.** 체크 항목의 실제 내용(증상·확인법·수정·라우팅)은 전부 거기에 `VC-nn`으로 있다.

판정 리포트는 규칙 ID를 인용한 줄로만 쓴다:

```
[VC-01] 불합격 — 사이드바만 cool gray, 본문 카드는 warm cream. 라우팅: 국소
[VC-02] 합격
[VC-07] 판정 불가 — 빈 상태 화면이 렌더되지 않음
```

- "판정 불가"를 합격으로 처리하지 않는다. 볼 수 없으면 볼 수 있게 만든 뒤 다시 본다.
- 클리셰/AI슬롭(`VC-06`)은 `references.md`의 "클리셰 후보" 목록을 이번 프로젝트 항목으로 덧붙여 본다.
- `UH` 중 매체가 `플로우`인 규칙은 화면 1장으로 판정하지 않는다. **해당 상태 화면을 안 만들었다면 그 자체가 결함**이므로 `판정 불가`로 남기고 화면을 만든 뒤 다시 본다.
- `context/visual-criteria.md`로 안 잡히는데 실제로 눈에 거슬리는 것이 있으면, 고치고 끝내지 말고 **새 `VC`로 등재**한 뒤 판정한다.

### C단계 실패 시 라우팅

**라우팅은 판정 시점에 즉흥으로 정하지 않는다** — 각 `VC` 규칙에 미리 박혀 있는 `라우팅` 필드를 따른다. 규칙에 없으면 그 규칙이 미완성이다.

1. **국소적 결함** (표면 속성 하나의 문제) → 그 속성만 고쳐 C단계 재검. B단계로 돌아가지 않는다.
2. **방향 자체가 틀림** (국소 조정으로 안 고쳐지는 구조적 문제) → B단계로 회귀, 다른 후보 선택 또는 재발산.
3. **반복 실패** (B단계에서 후보를 바꿔도 같은 이유로 계속 탈락) → 0단계로 에스컬레이션.

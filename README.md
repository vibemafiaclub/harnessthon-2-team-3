# oss-design-harness

**현업 디자이너의 판단 기준(안목)을 추출해, 에이전트에 최적화된 형태로 재구성하는 Figma-네이티브 디자인 하네스.**

VIBE MAFIA CLUB 하네스톤 2회차(2026-09-05)를 계기로 이너서클 코파운더들과 함께 만드는 오픈소스 프로젝트입니다.
지향점: `ui-ux-pro-max` 급, 현업에서 쓸 수 있는 수준의 skill.

## 이 레포의 상태

**완전 빈 템플릿입니다.** 뼈대(A/B/C/0 4단계 구조, 파일 포맷)만 있고, 실제 판단 기준 내용은 비어 있습니다.

- 판단 기준의 실제 내용(예: "무엇을 보고 고급스럽다고 판단하는가")은 **하네스톤 참가자·코파운더가 실제로 채워야** 의미가 있습니다.
- 미리 채워서 예시로 주면, 참가자가 자기 안목을 꺼내는 대신 이미 있는 답을 검토하는 일이 되어 버려 원래 목적(다양한 디자이너의 독립적 안목 수집)이 오염됩니다.
- 그래서 지금은 각 섹션에 `TODO`만 있고, 예시 2~3개만 남깁니다.

## 프레임워크 — 4단계 판단 구조

디자이너가 일하는 **순서**를 그대로 흉내내지 않습니다. 사람이 순서대로 일하는 이유의 상당수는 사람의 기억력·주의력 한계를 우회하는 것이지, 결과가 좋아지는 진짜 원인이 아닙니다. 대신 각 단계가 실제로 하려던 일(**판단 기준**)만 뽑아서, 에이전트가 잘하는 방식(병렬 생성, 다각도 교차 비평)으로 다시 구현합니다.

| 단계 | 시점 | 하는 일 |
|---|---|---|
| **0. 요구사항 정렬** | 화면을 만들기 **전** | 뭘 만들지 자체가 불확실할 때, 레퍼런스/시나리오를 보여주고 반응(좋다/싫다+이유)을 받아 암묵적 판단기준을 뽑아낸다. 라벨형 질문("모던한 게 좋으세요?") 금지. **산출은 후보가 아니라 제약** — 3막(읽기·자극·역추출) 절차는 SKILL.md 참조. |
| **B. 발산·수렴** | 만드는 도중, 정답이 여러 개일 때 | 독립적인 축(무드/밀도/난이도 등)을 먼저 나누고, 축마다 후보를 병렬 생성해 비교·수렴한다. |
| **A. 구조적 사실 검증** | 다 만든 후 | 데이터로 예/아니오 확인 가능한 것 (spacing, 컴포넌트 재사용, 네이밍, variant 존재 여부). |
| **C. 미적·게슈탈트 판단** | 다 만든 후 | 스크린샷을 렌더해서 실제로 봐야만 아는 것 (색온도 일관성, 위계, 여백 리듬, 클리셰 여부, 엣지케이스 완성도). |

C단계에서 탈락하면 원인에 따라 세 갈래로 라우팅한다 — ① 국소 결함(그 속성만 고쳐 C 재검) ② 방향 자체가 틀림(B로 회귀) ③ 반복 실패(0으로 에스컬레이션). 재시도 상한을 두고, 최종 판단은 항상 사람이 내린다.

자세한 배경·논리 검증 과정은 킥오프 자료(`docs/concept.md`) 참고.

## 판단 기준은 어디에 사는가

기준을 SKILL.md에 인라인으로 쓰지 않고 `context/`로 분리한다 — SKILL.md는 매 단계 전부 로드되지만 `context/`는 해당 단계에서만 읽히고, 참가자가 채워야 할 자리도 분명해진다.

- **`context/*.md` — 하네스 내장 지식.** 프로젝트가 바뀌어도 남고, 프로젝트를 거칠수록 규칙이 누적된다. 여기에 기준값(hex, px)을 하드코딩하지 않는다. *무엇을 어떻게 보는가*만.
- **`brief.md` — 프로젝트별 값.** `context/`의 항목에 이번 프로젝트의 수치를 주입한다.
- **`references.md` — 이번 프로젝트에서 소싱한 레퍼런스.** 프로젝트와 함께 버려진다. 다음에도 쓸 메커니즘만 `PT-nn`으로 `context/ux-patterns.md`에 승격한다.

모든 규칙에 ID(`PT` / `AX` / `VC` / `CH` / `UH`)를 달고, 판정·후보 선택 시 그 ID를 인용하게 한다. 읽었는지 사후 검증이 되고, 덤으로 **어떤 규칙이 실제로 발동했는지**가 로그로 쌓여 규칙 자체의 품질 데이터가 된다.

## 구조

```
.claude/skills/oss-design-harness/SKILL.md   # 하네스 본체 — 4단계 절차 + context/ 로드 지시
.claude/skills/oss-design-harness/context/    # 하네스 내장 판단 지식 (프로젝트를 넘어 누적)
  ├ ux-patterns.md                            #   0·B단계 — 문제 구조 → 화면 패턴(PT) / 축 후보(AX)
  ├ reference-channels.md                     #   0·B-2단계 — 어느 창구로 가는가 + 채널별 사각지대(CH)
  ├ visual-criteria.md                        #   C단계 — 봐야 아는 것의 판별 기준(VC)
  └ usability-heuristics.md                   #   A·C단계 — 사용성 하한선, 닐슨 10원칙(UH) · 유일하게 채워진 문서
templates/core-problem.md                     # 0단계 산출물 양식 — 핵심 사용자·핵심 문제·제약(D)·결정지점(DP)
templates/brief.md                            # 0단계 산출물 양식 — 반응 원문·역추출 판단기준·토큰·A단계 기준값
templates/references.md                       # B-2 산출물 양식 — 무드보드가 아니라 메커니즘 카드
templates/decisions.md                        # B단계 산출물 양식
docs/concept.md                               # 컨셉 스펙 전문 (배경·경쟁 포지셔닝·논리 검증 과정)
docs/prd1.md                                  # 연습용 예시 PRD (하네스톤 사전 공개본)
.mcp.json                                     # uibowl MCP 등록 — reference-channels.md의 CH-01이 전제
```

## 사용법 (참가자용)

1. Figma 파일을 열고, 이 레포를 프로젝트 루트로 해서 Claude Code(또는 다른 코딩 에이전트)를 실행한다.
2. `.claude/skills/oss-design-harness/SKILL.md`의 각 단계 `TODO`와 `context/`의 규칙 `TODO`를 채워 넣는다 — 이게 당신의 판단기준을 코드화하는 작업이다. **판단 기준의 내용은 SKILL.md가 아니라 `context/`에 규칙 단위(5필드 + ID)로 쓴다.**
3. 0단계 결과는 `core-problem.md`(문제 정의)와 `brief.md`(반응·판단기준), B단계 결과는 `decisions.md`에 남긴다 (템플릿을 프로젝트 폴더로 복사해서 사용).
4. 완성된 SKILL.md는 팀/코파운더와 공유해 비교한다.

# Decisions — 청첩장모임 스케줄러

## 식별된 독립 축 (B-1)

축 후보는 `DP-nn`에서만 뽑는다. `context/ux-patterns.md`의 `AX` 표를 먼저 검토하고, 이 프로젝트의 결정 지점에 맞춰 좁혔다.

| 축 | 출처 DP | `AX` 대응 | 양 끝 | 왜 이게 축인가 |
|---|---|---|---|---|
| **축 1 — 홈의 조직 원리** | DP-02 (+ DP-05 종속) | `AX-03` 변형 | `행동 큐`(지금 할 일만) ↔ `상태 보드`(단계별 칸) ↔ `캘린더`(시간 축) | 20~30건이 동시에 흐를 때 무엇을 기준으로 조직하느냐가 `core-problem.md §2`의 반증 조건과 직결된다. 실패 모드가 행동 누락이면 큐, 조회 실패면 보드/캘린더 |
| **축 2 — 편성의 주도권** | DP-03 | `AX-02` 변형 | `사람이 다 정한다`(다중선택 → 묶기) ↔ `앱이 제안하고 사람이 고친다`(태그 기반 자동 그룹핑) | 40~60명 규모에서 조작 횟수가 수 배 차이 난다. `D-02`(N:M)와 `D-03`(미배정 추적)을 각 끝이 서로 다르게 잘 푼다 |
| **축 3 — 비주얼 무드** | DP-06 | `AX-01` | `운영 도구`(밀도 높고 상태가 주인공) ↔ `예식 정서`(여백 넓고 정서가 주인공) | 도메인(가장 정서적인 이벤트)과 실제 작업(운영·조율)이 정면으로 어긋난다. 이 긴장의 해소 지점이 팔레트·서체·밀도를 전부 가른다 |

**독립성 확인** — 한 축의 선택이 다른 축의 선택을 강제하지 않는지 교차 확인했다.

| | 축 1을 강제하는가 | 축 2를 강제하는가 | 축 3을 강제하는가 |
|---|---|---|---|
| **축 1** (홈 조직) | — | ✗ 홈이 큐여도 편성은 수동/자동 둘 다 가능 | ✗ 큐도 정서적으로, 캘린더도 도구적으로 그릴 수 있다 |
| **축 2** (편성 주도권) | ✗ 자동 제안이어도 홈은 캘린더일 수 있다 | — | ✗ 무관 |
| **축 3** (무드) | ✗ 정서적이어도 큐를 쓸 수 있다 | ✗ 무관 | — |

→ 세 축은 독립이다. 다만 **축 3은 축 1·2보다 약하게 독립**이다 — 극단적 `예식 정서`는 여백을 요구해 고밀도 리스트(축 1의 큐/보드)와 충돌한다. 이 결합은 `MB-05`의 부분 채택 시험으로 검증한다: 사람이 "1안인데 무드는 3안처럼"을 고를 수 있으면 독립이고, 못 고르면 축 3은 축 1에 종속이었던 것이다.

**폼팩터는 축이 아니다.** 산출물은 모바일 화면이고 그건 0단계에서 정해진 제약이다(`brief.md` 모바일 사용 맥락: 390 설계 / 360 하한).

**후보 자격 사전 필터** — `PT-02`(가용성 매트릭스)는 성립 조건에 데스크톱 폭이 필요하므로 **축 1의 후보로 올리지 않는다**. DP-05의 선택지 (c)가 여기서 탈락하고, 모바일 대안(날짜별 리스트 + 참석자 뱃지)으로 대체된다.

## 축별 후보·비교·선택 (B-3)

후보는 축마다 3개이고, 셋은 취향이 아니라 **위험도 축**(`MB-01`) 위에 놓았다 — 컨벤션 그대로(무난) / 수렴 결과(추천) / 타도메인 메커니즘을 더 민 것(도전). 이 좌표가 그대로 B-3.5 목업 3안의 열이 된다.

**수렴 게이트**: `ref-02`(Airbnb)의 *"응답 마감이 있는 것은 시간축이 아니라 큐에 있다"*에서 왔다. 우리 페르소나에서 성립하는 이유 — 회신 마감·무응답·충돌 3종 신호가 전부 캘린더 격자 위에 놓을 자리가 없는 것들이고(`ref-03`의 overdue와 같은 성질), 그런데 그게 정확히 놓치면 안 되는 것들이다.

**수렴 게이트**: `ref-12`(Radix/Tailwind)의 *"색온도는 면 구조와 독립 변수이고, warm은 중간 단계 chroma가 cool의 1/3~1/4"*에서 왔다. 우리 페르소나에서 성립하는 이유 — 야간 저조도에서 회신 상태를 확인하는 사용(`brief.md` 조명·환경)에서, 액센트가 뉴트럴과 경쟁하지 않는 것이 곧 판독 속도다.

## 축 → `DESIGN.md` 반영 점검 (`DS-04`)

`DESIGN.md`는 **1안(추천안)의 값**으로 작성했다. 2안·3안을 고르시면 `DESIGN-v2.md`로 새로 쓰고 원본을 덮어쓰지 않는다.

| 축 | 내려앉은 섹션 | 구체적으로 어느 값 |
|---|---|---|
| 축 1 — 홈의 조직 원리 | `## Layout` · `## Components` | `mobile.primaryNavigation` 성격의 결정이 **탭바 4개(할일/사람/모임/달력)**로, 그리고 첫 탭이 목록이 아니라 행동 큐라는 것이 `list-row`의 상태 엔트리 `-alert`와 `-empty`로 내려앉았다. `ref-01`의 "섹션이 비면 사라진다"가 `-empty`의 사용 범위를 큐 전체가 빈 경우 하나로 좁혔다 |
| 축 2 — 편성의 주도권 | `## Components` | `checkbox`의 상태 3종(`-selected` / `-indeterminate` / 기본)과 `app-bar-contextual`, 그리고 `## Do's and Don'ts`의 "롱프레스 단독 진입 금지". 상시 선택이라는 선택이 **체크박스가 항상 노출된다**는 컴포넌트 정의가 됐다 |
| 축 3 — 비주얼 무드 | `## Colors` · `## Typography` · `## Shapes` | 정서 허용 지점 1개 → `colors`가 뉴트럴 8 + 액센트 계열 4로, 액센트가 쓰이는 자리가 산문에서 **셋으로 명시**됐다. 서체는 세리프를 들이지 않고 Pretendard 단일 5크기 · weight 2종 |

**어느 섹션에도 안 걸린 축**: 없음. **한 섹션에 여러 축이 몰린 경우**: `## Components`에 축 1·2가 함께 걸렸으나, 축 1은 `list-row`의 상태를, 축 2는 `checkbox`·`app-bar-contextual`을 각각 정의해 대상이 겹치지 않는다 — 독립성은 유지된다.

### 하네스 전용 값을 `DESIGN.md`에 넣지 않은 이유

사용자 지시("design.md를 그대로 가져다가 사용")에 따라 **공식 스펙의 front matter 키 9개만** 썼다. 하네스 템플릿(`templates/DESIGN.md`)이 추가했던 `mobile:` · `harness:` 블록은 **스펙에 없는 확장**이므로 제외하고, 그 값들을 스펙이 허용하는 자리로 옮겼다.

| 원래 `mobile:`/`harness:` 값 | 옮긴 곳 |
|---|---|
| `designViewportWidth` 390 | `components.screen.width` (스펙의 유효 속성 `width`) |
| `minViewportWidth` 360 | `## Layout` 산문 — "360px에서 무너지지 않아야 한다" |
| `minTouchTarget` 48 | `components.button.height` · `checkbox.height` · `tab-bar-item.height` · `date-cell.height` |
| `minBodyFontSize` 15 | `typography.body.fontSize` |
| `safeAreaTop` / `safeAreaBottom` | `spacing.safe-top` / `spacing.safe-bottom` (스펙: "any descriptive string key is valid") |
| `primaryNavigation` 탭바 | `## Layout` 산문 + `components.tab-bar-item` |

**A단계 `SC` 검사 기준값 (하네스 전용)**

| 항목 | 기준 |
|---|---|
| `layerNamingConvention` | `역할/상태` — 예: `ListRow/Alert`, `Button/PrimaryPressed`. `DESIGN.md`의 컴포넌트 키를 PascalCase로 옮긴 것 |

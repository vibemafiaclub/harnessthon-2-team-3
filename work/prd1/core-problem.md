# 핵심 문제 정의서 — 청첩장모임 스케줄러

## 1. 핵심 사용자 — `P1-주 편성자`

유저스토리 3개를 상한으로 후보를 벌렸다.

| 후보 | 가르는 DP | 판정 |
|---|---|---|
| `P1-주 편성자` (커플 중 편성 부하를 지는 쪽) | DP-02·DP-03·DP-04·DP-05 | ✅ 채택 |
| `P2-응답 지인` (초대받은 사람) | DP-01 | ❌ 탈락 — 작업량이 모임당 1회(회신 1번). 단 DP-01을 가르므로 §4에 남긴다 |
| `P3-배우자` (반대편 풀 관리자) | DP-04 | ❌ 탈락 — `P1`과 작업 종류가 동일하고, 다른 점은 *풀이 분리돼 있다*는 것뿐이다. 그건 사용자가 아니라 D-05 제약이다 |

**탈락 사유 한 줄**: `P2`는 부하가 1회여서, `P3`는 `P1`과 같은 일을 해서 탈락. 둘 다 DP는 가르므로 결정 지점으로만 남긴다.

| 필드 | 값 | 근거 |
|---|---|---|
| 규모 | 지인 **40~60명(최대 100+)** → 파생: 모임 **20~30건**. 두 경로로 계산해 수렴 확인 (아래) | PRD §3-1, §3-2, §3-3 |
| 빈도 | 결혼식 **3개월 전 ~ 2주 전**, 주말마다 모임 2~3건. 앱은 회신 확인 목적으로 **주 수회·1회 수십 초** | PRD §3-2, §3-6 |
| 성공 조건 | 40~60명이 **전원 어느 모임엔가 배정**되고 · 각 모임이 **확정 날짜**를 갖고 · **양가 일정이 겹치지 않는다** | PRD §4-1~5 |
| 실패 비용 | **비가역적·사회적**. 청첩장을 못 준 사람이 발생하면 결혼식 후에 되돌릴 방법이 없다. 마감(예식일)이 고정이라 지연이 곧 누락으로 굳는다 | PRD §1(직접 건네는 문화), §3-2 |

**규모의 두 경로 수렴 검증**
- 경로 A(사람에서): 60명 ÷ 모임당 3~6명(평균 4.5) ≈ 13건 + 1:1 관계 다수 → **20~30건**
- 경로 B(시간에서): 12주 × 주말 2~3건 ≈ **24~36건**
- → 두 경로가 **20~30건대에서 수렴한다.** 이 숫자가 `PT-01`(행동 큐)의 성립 조건 "동시 진행 15건 이상"을 만족시키고, 동시에 `PT-02`(매트릭스)의 "행 3~8 × 열 3~8"은 **모임 1건 안에서만** 성립함을 확정한다(전체 20~30건을 한 매트릭스에 넣을 수 없다).

## 2. 핵심 문제

> **수십 건의 조율이 서로 다른 상태로 동시에 흐르는데 그 상태를 보관하는 곳이 사람의 기억뿐이고, 마감(예식일)은 고정인데 진행은 남의 응답 속도에 달려 있다.**

**기존 대안(메신저 단체채팅방)이 왜 실패하는가**: 채팅방은 **상태가 없는 매체**다. 대화 내용은 남지만 "이 방이 지금 어느 단계인지"는 남지 않는다. 방이 1~2개일 때는 사람이 상태를 들고 있을 수 있지만, 20~30개가 되면 보관처가 무너진다(PRD §1 "예비부부 스스로도 놓치기 시작"). 더 결정적인 것은 **방이 모임 단위로만 존재한다**는 점이다 — *사람 단위*(한 사람이 여러 방에 걸침)와 *전체 단위*(방끼리 날짜가 겹침)의 뷰가 원리적으로 만들어질 수 없다. 기능이 부족한 게 아니라 **자료구조가 틀렸다.**

**문제의 구조**: 성격이 다른 세 문제가 한 덩어리로 보이는 것이다.

1. **집합 커버링** (사람 → 모임) — 40~60명을 모임으로 묶는다. 한 사람이 여러 모임에 걸칠 수 있으므로 *분할*이 아니라 *커버링*이다. 실패 모드는 **누락**.
2. **스케줄 매칭** (모임 → 날짜) — 후보일 제시 → 회신 수합 → 확정. 진행을 막는 것은 무응답이므로 실패 모드는 **정지**.
3. **자원 경합** (전체 → 캘린더) — 확정된 모임들이 주말이라는 희소 자원을 두고 경합한다. 실패 모드는 **충돌**.

상태 기계: `미배정(사람)` → `편성됨` → `후보 발송` → `회신 대기` → `회신 완료` → `확정` → `완료`

| PRD의 까다로운 경우 | 구조적 정체 |
|---|---|
| 한 사람이 여러 무리에 걸침 (§2-1) | 커버링 문제 — 사람↔모임이 N:M. 부산물: "이 사람은 어느 모임에서 청첩장을 받았나"를 사람 쪽에서도 볼 수 있어야 함 |
| 며칠씩 답이 없는 사람 (§3-4) | `회신 대기` 상태에 **시간 축**이 붙은 것. 부산물: 마감 도달 시 전체 응답 없이도 확정으로 강제 전이(부분 확정)가 필요 |
| 모임이 겹침 (§4-5) | 자원 경합. 부산물: **후보일을 제시하는 시점에** 이미 알려야 한다 — 확정 후 감지는 늦다 |
| 1:1로 만나야 하는 상사 (§3-3) | 모임 크기 1. 커버링의 특수해이지 예외가 아님 |
| 양가가 같이 나가는 모임 (§3-5) | 모임의 소유자가 2명(공동). 풀은 분리, 모임은 공유 |
| 2주 전 급한 모임 (§3-6) | 제시→회신→확정 사이클의 **압축**. 마감 기한이 며칠이 아니라 몇 시간 |
| 신랑/신부 풀 분리 (§2-3) | 소유자별 파티션. 단 캘린더 레이어에서는 합쳐진다 |

**반증 조건** — 이 정의가 틀렸다는 신호:
- 사용자가 홈에서 "지금 할 일"이 아니라 **전체 목록/캘린더를 먼저 찾는다면**, 실패 모드는 행동 누락이 아니라 조회 실패였던 것이고 `PT-01`이 아니라 상태 보드가 맞다.
- 모임 건수가 실제로 10건 이하로 수렴한다면 상태 보관 문제 자체가 없다 — 채팅방으로 충분했다는 뜻이다.
- 무응답이 실제로는 드물다면(응답률 90%+) 시간 축·부분 확정 설계가 전부 과설계다.

## 3. 설계 북극성과 제약

> **예식일까지 남은 시간 안에 "아직 청첩장을 못 준 사람"을 0으로 만드는 제품이다. 예쁜 청첩장을 만들거나 하객을 관리하는 제품이 아니다.**

| ID | 제약 | 근거 |
|---|---|---|
| D-01 | 어느 화면에서도 사용자가 "지금 뭘 해야 하나"를 스스로 계산하지 않는다. 상태 전이의 다음 행동을 앱이 지목한다 | §2 채팅방 붕괴 원인 |
| D-02 | 사람↔모임은 N:M이다. "한 사람은 한 모임"을 전제하는 화면을 만들지 않는다 | PRD §2-1, §4-1 |
| D-03 | **미배정 인원 수**는 항상 도달 가능한 곳에 있다. 누락이 최대 실패 비용이므로 이 숫자가 곧 진척도다 | §1 실패 비용 |
| D-04 | 무응답은 값이 아니라 **시간**이다. 회신 화면은 남은 시간과 미응답자를 함께 보여주고, 마감 도달 시 부분 확정 경로를 연다 | PRD §3-4, §4-3 |
| D-05 | 풀은 신랑/신부로 분리, 캘린더는 통합. 후보일을 고르는 순간 **상대편 확정 일정이 같은 화면에** 있어야 한다 | PRD §2-3, §4-5, §5 |
| D-06 | 모임 크기 1(1:1)과 소유자 2인(양가 동반)은 예외 화면이 아니라 같은 화면의 값이다 | PRD §3-3, §3-5 |

## 4. 결정 지점 — 자극으로 정할 것

| ID | 갈림길 | 선택지 | 왜 큰가 |
|---|---|---|---|
| **DP-01** | 초대받은 지인(`P2`)을 제품 경계 안에 넣는가 | (a) 로그인 없는 응답 링크 1장 (b) 지인도 앱 사용자 — "여러 커플의 요청을 한 번에" 화면 보유 | **제품 경계**를 가른다. (b)면 화면 수가 배로 늘고 양면 시장이 된다. 유저스토리 2번이 (b)를 요구하는 듯 보이지만, 조건 §5는 "예비신랑·신부 두 사람이 함께 쓰는 것"이라 충돌한다 |
| **DP-02** | 홈의 기본 뷰 | (a) 행동 큐 `PT-01` (b) 캘린더 (c) 모임 상태 보드 | §2 반증 조건과 직결. 실패 모드가 행동 누락이면 (a), 조회 실패면 (b)/(c) |
| **DP-03** | 모임 편성의 주 동선 | (a) 사람 목록에서 다중선택 → 묶기 (b) 빈 모임 만들고 채우기 (c) 관계 태그 기반 자동 제안 후 수정 | 40~60명 규모에서 (a)와 (b)는 조작 횟수가 수 배 차이. D-02(N:M)를 (a)가 더 잘 표현하지만 미배정 추적은 (b)가 쉽다 |
| **DP-04** | 커플 두 사람의 분리 방식 | (a) 계정 2개 + 공유 워크스페이스, 항목마다 담당 표시 (b) 단일 계정 공유, 신랑/신부 필터 | D-05의 구현 형태를 가른다 |
| **DP-05** | 회신 수합 화면의 축 | (a) 날짜별 리스트 + 참석자 뱃지 (b) 사람별 리스트 (c) 매트릭스 `PT-02` | (c)는 데스크톱 폭을 요구해 **후보 자격 없음**(`PT-02` 명시). (a)/(b) 중 결정 필요 |
| **DP-06** | 화면이 어느 얼굴을 하는가 | (a) 운영 도구 — 밀도 높고 상태가 주인공 (b) 예식 정서 — 여백 넓고 정서가 주인공 (c) 도구 위에 정서를 좁은 한 요소로 격리 | 도메인(인생에서 가장 정서적인 이벤트)과 실제 작업(운영·조율)이 정면으로 어긋난다. 이 긴장을 어디서 해소하느냐가 팔레트·서체·밀도를 전부 가른다. `AX-01`의 이 프로젝트 버전 |

**결정 상태** (2막 폴백 후 갱신)

| DP | 상태 | 결론과 근거 |
|---|---|---|
| DP-01 | **확정** | (a) 로그인 없는 응답 링크. PRD §5가 "두 사람이 함께 쓰는 것을 전제"라고 못박아 양면 시장으로 넓히지 않는다. 유저스토리 2번은 응답 링크 안의 **연락처 기반 크로스 힌트**로 부분 충족 (`ASSUMP-06`) |
| DP-02 | **B-3.5로 이월** | 목업 3안에서 사람이 고른다 |
| DP-03 | **B-3.5로 이월** | 목업 3안에서 사람이 고른다 |
| DP-04 | **확정** | (b) 단일 공유 워크스페이스 + 항목별 담당 표시. PRD §4-5가 "합쳐서 한눈에"를 요구하므로 합치는 것이 기본, 나누는 것이 필터 (`ASSUMP-16`) |
| DP-05 | **B-3.5로 이월** | 축 1(홈 조직 원리)에 종속되므로 3안 안에서 함께 갈린다 |
| DP-06 | **B-3.5로 이월** | 목업 3안의 비주얼 무드가 여기서 갈린다 (`MB-04`) |

**자극 우선순위**: DP-01(제품 경계) → DP-02(홈) → DP-03(편성 동선) → DP-06(무드). DP-04·DP-05는 앞 셋이 정해지면 상당 부분 따라온다.

**2막은 폴백으로 실행했다** — 요구사항 문서의 상황 서술을 반응으로 간주해 역추출(`brief.md`의 자극·반응 표). 사람이 실제로 고르는 자리는 **B-3.5 목업 보드**로 이월했고, 위 표의 `이월` 항목이 거기서 결정된다.

## 6. 비목표

- 청첩장 자체의 디자인·발송(모바일 청첩장 제작)
- 하객 명단·축의금 관리 (결혼식 당일 이후의 문제)
- 식당 예약·장소 추천 (모임의 *언제*만 다루고 *어디서*는 다루지 않는다)
- 지인 쪽의 개인 일정 관리 앱 (DP-01이 (a)로 정해질 경우)

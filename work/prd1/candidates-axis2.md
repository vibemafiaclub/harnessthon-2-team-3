# 축 2 — 편성의 주도권 · 후보 3안 (B-3)

> **축 정의**(`decisions.md` B-1, 출처 `DP-03`): 40~60명을 20~30개 모임으로 묶는 동선에서 **누가 먼저 움직이는가**.
> 양 끝: `사람이 다 정한다`(다중선택 → 묶기) ↔ `앱이 제안하고 사람이 고친다`(태그 기반 자동 그룹핑).
>
> **범위 밖**: 축 1(홈의 조직 원리)과 축 3(비주얼 무드). 아래 세 후보는 **홈이 큐든 캘린더든 상태 보드든 그대로 성립**하도록 기술했다(편성 화면은 홈에서 진입하는 별도 화면이고, 홈이 무엇이냐는 진입점 문구만 바꾼다). 색·서체·무드는 한 줄도 언급하지 않는다.
> 세 후보는 취향이 아니라 **위험도**로 갈린다: A(관습에 가장 가까움) → B(레퍼런스 수렴) → C(관습에서 가장 멂).

## 0. 공통 전제 — 조작 횟수 계산 모델

세 후보의 탭 수를 같은 자로 재기 위해 아래를 고정한다. **대략치이고, 값 자체보다 후보 간 비(比)가 결론이다.**

| 기호 | 값 | 근거 |
|---|---|---|
| 사람 수 `P` | **55명** | `core-problem.md` 40~60명의 중앙 |
| 모임 수 `G` | **25건** | 20~30건의 중앙. 그중 **1:1 모임 5건**(PRD §3-3) |
| 총 소속 관계 `M` | **90건** | 25건 × 평균 3.6명. `P=55`이므로 **중복 소속 35건**(약 25명이 2개 이상에 걸침 — PRD §2-1) |
| 세션 | **수십 초 × 주 수회** | `brief.md` 모바일 사용 맥락 |
| 폭 | 390px 설계 / **360px 하한** | 같은 곳 |
| 터치 타깃 | **48dp**, 타깃 간 8dp | `ref-07` |

**세는 규칙**: 탭 1회 = 손가락 1회 접촉. **스크롤과 텍스트 입력은 탭에 넣지 않고 따로 집계**한다(모임 이름 타이핑 1회는 탭 1회보다 훨씬 비싸므로 섞으면 비교가 왜곡된다).

`ASSUMP-A2-01` — 중복 소속 35건 중 **20건은 "같은 사람 묶음이 연달아 두 모임에 들어가는" 형태**(예: 대학 동기 4명이 그대로 동네 친구 모임에도)라고 가정한다. 이 비율이 후보 B의 이득 전부를 만들므로, 실제로 중복이 **개별 산발**이면 B의 탭 이득은 사라진다(→ B "깨지는 조건").

## 후보 A — 다중선택 → 일괄 배정 (관습 그대로)

**한 줄**: 사람 목록에서 체크박스로 여러 명을 고르고, 하단 액션 바로 "모임에 추가"를 눌러 목적지를 고른다. 액션이 끝나면 선택이 풀린다.

### A-1. 동선

1. 홈에서 `편성` 진입 → **사람 목록**(2줄 행, 72dp). 좌측에 리딩 체크박스가 **상시 노출**(롱프레스 진입 안 씀 — `ref-06` "안 가져올 것", 클리셰 판정된 항목).
2. 사람 행의 체크박스를 탭해 n명 선택 → 상단 앱바가 **컨텍스추얼 앱바로 치환**(`ref-07`): 좌측 `X`(해제), 제목 자리 `3명 선택`.
3. 하단에 **액션 바(80dp)** 가 올라온다: `모임에 추가`.
4. 탭하면 **바텀시트**: 최상단에 `+ 새 모임 만들기`, 그 아래 `최근 만든 모임` 캐러셀, 그 아래 전체 모임 리스트(`ref-06`).
5. 목적지를 고르면 부착되고 **선택이 자동 해제**된다. 사람 행은 목록에서 **사라지지 않고** 줄2의 소속 배지가 갱신된다(`ref-09` 부착≠이동).
6. 2~5를 25번 반복한다.

### A-2. 조작 횟수

| 항목 | 계산 | 탭 |
|---|---|---|
| 사람 체크 | 소속 관계 `M`=90건마다 1회(중복 소속은 다시 체크) | 90 |
| 하단 `모임에 추가` | 25 | 25 |
| 시트에서 `+ 새 모임` | 25 | 25 |
| 시트에서 목적지 확정 | 25 | 25 |
| 선택 해제 | 자동 | 0 |
| **합계** | | **165탭 + 텍스트 입력 25회 + 목록 스크롤 25회분** |

1:1 모임 5건은 **1명 위해 4탭**이라 단위 효율이 가장 나쁘다(모임당 4탭 중 체크는 1탭뿐).

### A-3. N:M(D-02) 표현

- 행은 **2줄(72dp)**. 줄1 = 이름 + 소유자 뱃지(신랑/신부/양가), 줄2 = **소속 요약**.
- `ref-09`의 한계(칩 3개 이상 붕괴)를 **칩을 안 써서** 피한다. 줄2는 `대학 동기 외 2 · 3개 모임` 형태의 **대표 1개 + 개수 배지**. 색 칩 나열은 `references.md`에서 **클리셰로 판정된 항목**이라 애초에 배제.
- 소속 0개면 줄2가 `아직 어느 모임에도 없음`으로 **비어 있는 쪽이 튄다**(`brief.md` 상태 표현 축).
- 390px 폭 검산: 좌 16 + 체크 48 + 텍스트 시작 72dp 기준 → **텍스트 가용 폭 약 302px**. 360px에서는 272px. 대표 모임명을 **8자에서 말줄임**하면 `… · 3개 모임`이 들어간다. `ASSUMP-A2-02`(말줄임 자릿수는 실측 근거 없음 — 사각지대 2).

### A-4. 미배정 추적(D-03)

- 사람 목록 **최상단에 `미배정` 섹션을 고정**하고, 섹션 헤더에 `아직 어느 모임에도 없는 사람 12명`. 스크롤해도 헤더가 붙어 있다.
- `ref-07`(Notion `No Status` 컬럼 = 동등한 하나의 그룹) + `ref-06`(QuickBooks `37 to Review` = 숫자 + 상태 서술)의 조합. 가로 칸반은 360px에서 불가하므로 **세로 섹션으로 변형**했다.
- `ASSUMP-A2-03` — **미배정 카운트를 목록 상단 고정 섹션 헤더에 두는 형태는 우리가 발명한 것이다.** `references.md` 사각지대 1(미분류 잔여 카운트 UI에 실측 근거 없음)에 정확히 해당한다. 검증 안 됨.

### A-5. 애매한 사람 · 1:1

- **여기가 A의 구조적 약점이다.** "어느 모임에 넣어야 좋을지 애매"(PRD §2-1)를 표현할 자리가 없다. 애매한 사람은 (a) 아무 데나 넣어지거나 (b) 미배정에 계속 남는다. 둘 다 정보가 아니다 — (b)는 "아직 안 봤다"와 "봤는데 못 정했다"가 구분되지 않는다.
- `ref-10`의 3지선다는 **A에 들어갈 자리가 없다.** A는 사람이 먼저 움직이므로 앱이 물어볼 시점 자체가 없기 때문이다. 완화책은 사용자가 `보류` 모임을 직접 만드는 것뿐인데, 그건 20~30개 모임 목록에 가짜 모임 1개를 섞는 것이라 `D-03`의 카운트를 오염시킨다.
- **1:1**: 1명 체크 → 모임 만들기. **화면이 갈라지지 않는다** → `D-06` 준수. 다만 A-2에서 본 대로 탭 효율이 최악.

### A-6. 근거 ref (1:1 대응 아님)

- `ref-07`(상단 컨텍스추얼 앱바 = 개수 + 탈출구) **+** `ref-06`(하단 시트 = 실행) 을 **쪼개서 상하 분리**했다. M3 원본은 일괄 액션도 상단에 두지만, 390px 한 손에서 상단 우측은 엄지 사각지대라 그대로 쓰지 않았다.
- `ref-09`는 **부착 모델만 취하고 표현(컬러 칩)은 버렸다** — 20~30개 모임에 색 20~30종은 구분 불가.
- `ref-06`+`ref-07`을 그대로 쌓으면 그게 바로 "관습"이고, A는 의도적으로 거기서 멈춘 안이다.

### A-7. PT 인용과 성립 조건 대입

**`PT-A2-01` 다중선택 일괄 배정** — `ux-patterns.md`에 미등재. 아래 §5에 5필드로 초안을 적었다(등재 대기).

| 성립 조건 | 이 프로젝트 값 | 판정 |
|---|---|---|
| 대상 항목 30건 이상 | 55명 | ✅ |
| 한 번에 고르는 부분집합 크기 2~10 | 모임당 3~6명 | ✅ |
| 목적지 종류 ≤ 30 | 모임 20~30건 | ⚠️ **상한 접촉** — 시트 안에서 목적지를 찾는 비용이 25건에서 이미 스크롤이다 |
| 최소 폭 | 360px | ✅ (`ref-07` 규범이 360 기준) |
| 세션 길이 | 수십 초 | ❌ **불충족** — 165탭은 15~20세션에 걸쳐야 끝난다 |

### A-8. D-01~D-06 · 깨지는 조건

| 제약 | 판정 |
|---|---|
| D-01 (앱이 다음 행동 지목) | ⚠️ **약함**. 사람 목록은 "다음에 누구를 묶을지"를 지목하지 않는다. 미배정 고정 섹션이 최소한의 대응이지만, 그건 *무엇이 남았나*이지 *다음에 뭘 하라*가 아니다 |
| D-02 (N:M) | ✅ 부착 후에도 행이 남고 개수 배지로 표현 |
| D-03 (미배정 상시) | ✅ 고정 섹션 헤더 (단 `ASSUMP-A2-03`) |

**깨지는 조건**

## 후보 B — 목적지 핀 + 선택 유지 (추천)

**한 줄**: **담을 곳을 먼저 고정한다.** 하단 바에 목적지 모임이 "핀"으로 걸려 있는 동안 사람 행을 한 번 탭하면 곧바로 부착되고, 핀은 사람이 바꿀 때까지 유지된다. 다중선택은 사라지지 않고 **집합을 여러 모임에 연달아 붙이는 용도**로 남는다.

### B-1. 동선

1. `편성` 진입 → 사람 목록. **하단 핀 바(80dp)** 가 상시 떠 있다. 초기 상태: `담을 곳을 고르세요 · 미배정 55명`.
2. 핀 바를 탭 → 바텀시트(`+ 새 모임` / 최근 모임 캐러셀 / 전체 목록 / **`보류` 핀**). 목적지를 고르면 핀 바가 `담는 곳: 대학 동기 (2명) · 미배정 55명`으로 바뀐다.
3. **핀이 걸린 동안 사람 행 본문 탭 = 즉시 부착.** 부착된 행은 **사라지지 않고** 우측에 채워진 점이 켜지고 줄2 개수 배지가 `+1` 된다. 핀 바의 인원수와 미배정 카운트가 **같은 탭에 동시에** 움직인다.
4. 다음 모임으로 넘어갈 때는 핀 바만 다시 탭해 목적지를 바꾼다(**핀 해제 탭 없음 — 교체가 곧 해제**).
5. 같은 사람 묶음을 두 모임에 넣을 때는 **좌측 체크박스**로 집합을 만들고 핀 바 우측 `선택 4명 담기`를 누른다. **액션 후에도 선택이 유지**되므로(`ref-08`) 핀만 바꿔 한 번 더 누르면 끝이다.
6. 선택 집합은 사용자가 상단 `X`를 눌러야 풀린다.

**두 제스처가 한 행에 겹치는 것을 어떻게 막는가**: 좌측 48dp = 체크박스(집합), 행 본문 = 부착. 겹치지 않게 8dp를 띄운다(`ref-07`). 그리고 **핀이 없을 때는 행 본문 탭 = 사람 상세**로 동작하므로, 핀 바가 곧 "지금 어느 모드인가"의 상시 표시다(상단 앱바 + 하단 핀 바 두 곳에서 모드를 알린다).

### B-2. 조작 횟수

| 항목 | 계산 | 탭 |
|---|---|---|
| 목적지 만들기/고르기 | 25 × 2(핀 바 탭 + 시트 선택). `+ 새 모임`은 이 2탭 안 | 50 |
| 부착 | `M`=90 − 재사용 20(`ASSUMP-A2-01`) = 70회 × 1탭 | 70 |
| 집합 만들기(재사용분) | 20건을 만든 체크 5회 | 5 |
| 핀 해제 | 교체가 곧 해제 | 0 |
| 선택 집합 해제 | 5 | 5 |
| **합계** | | **130탭 + 텍스트 입력 25회 + 스크롤 25회분** |

**A 대비 −21%**(165 → 130). 이득의 출처는 두 개다: ① 부착이 `체크 + 액션 + 목적지` 3탭에서 **1탭**으로 압축, ② 반복 목적지 선택을 핀이 흡수. 1:1 5건도 **핀 2탭 + 부착 1탭 = 3탭**으로 A(4탭)보다 낫다.

### B-3. N:M(D-02) 표현

- 행 구조는 A와 같다(2줄 72dp, 대표 1개 + 개수 배지). 칩 나열을 안 쓰므로 `ref-09` 한계를 그대로 피한다.
- **B만의 것**: 부착 순간 행이 사라지지 않고 **개수 배지가 그 자리에서 카운트업**한다. "부착은 이동이 아니다"(컨벤션 10)를 문구가 아니라 **동작으로 증명**한다. `ref-09`가 개념으로만 가진 것을 우리 규모에 맞게 옮긴 지점.
- 핀에 걸린 모임에 **이미 속한 사람**은 행 우측 점이 채워져 있어, 같은 사람을 두 번 누르는 낭비가 사전에 보인다(A에는 이 정보가 없다).

### B-4. 미배정 추적(D-03)

- **하단 핀 바 우측에 상시.** `담는 곳: 대학 동기 (4명) · 미배정 41명`. 화면에서 가장 자주 보는 대역(엄지가 닿는 하단)에 **진척도와 목적지가 한 줄에** 있다.
- 목록 최상단의 `미배정` 고정 섹션은 A와 동일하게 유지(두 곳에 나오는 것은 `ref-06`의 QuickBooks 구조 — 계좌 타일 + 탭 라벨 2곳 노출 — 과 같다).
- **탭 1회 = 카운트 −1** 이 눈에 보이는 것이 B의 심리적 핵심이다. 165탭짜리 일을 "숫자가 줄어드는 일"로 바꾼다.

## 후보 C — 태그 기반 자동 그룹핑 + 제안 검수 (도전)

**한 줄**: 사람에게 **관계 태그**만 달아두면 앱이 20~30개 모임 초안을 먼저 만들고, 사람은 제안을 **한 건씩 검수**한다. 확신이 낮은 경계 사례만 3지선다로 물어본다.

### C-1. 동선

1. **태그 부여**(선행 작업) — 사람 목록에서 다중선택 → 하단 `관계 태그 달기` → `대학 / 직장 / 동네 / 가족 / 상사` 등. **모임이 아니라 태그**를 붙이는 것이므로 한 사람에게 여러 태그가 겹쳐 붙는다.
2. 앱이 태그 교집합으로 **모임 초안을 만든다.** 초안은 확정이 아니다 — 목록에서 **점선 테두리 + `제안` 상태**로 존재하고, 확정된 모임과 시각적으로 구분된다(컨벤션 11, Spotify 보조 관찰의 "제안 ≠ 확정"을 상태 분리로 표현).
3. **제안 검수 큐**: 하단에서 카드가 한 장씩 올라온다. 카드 = `대학 동기 · 4명` + 이름 4줄 + `이대로 확정` / `고치기`.
4. `고치기`를 누르면 그 4명에 체크박스가 붙은 편집 상태로 펼쳐진다(빼기/더하기). 여기서 **후보 A의 동선이 부분적으로 재등장**한다 — C는 A를 버리는 게 아니라 **A를 예외 경로로 밀어낸다.**
5. 앱이 확신하지 못한 사람(태그가 2개 이상 겹치거나 어느 태그도 3명 미만)은 **경계 사례 카드**로 따로 온다: `김민수 — 대학 동기이면서 동네 친구입니다` + **`대학 동기에 / 동네 친구에 / 아직 모르겠다`** 3지선다(`ref-10` 그대로).
6. `아직 모르겠다`는 **미배정 카운트에 계속 잡히는 `보류`**로 간다. 큐 끝에 다시 오지 않는다(같은 질문 반복 금지).
7. **`전부 확정`은 만들지 않는다.** 일괄 확정은 검수를 건너뛰게 만들어 컨벤션 11을 정면으로 깬다. 확정은 항상 그룹 단위 1탭이다.

### C-2. 조작 횟수

| 항목 | 계산 | 탭 |
|---|---|---|
| 태그 부여 | 태그 5종 × (체크 평균 11명 + 액션 2탭) = 5 × 13 | 65 |
| 제안 그룹 확정 | 25 × 1 | 25 |
| 제안 수정 | 25건 중 8건이 수정 필요(정확도 68% 가정) × 3탭 | 24 |
| 경계 사례 3지선다 | 12건 × 1 | 12 |
| 보류 인원 재처리 | 5명 × 3탭 | 15 |
| **합계** | | **141탭 + 텍스트 입력 0~5회 + 스크롤 소량** |

**여기가 C의 진짜 이득이다**: 탭은 A와 B 사이(141)지만 **모임 이름 타이핑 25회가 0~5회로 사라진다**(앱이 `대학 동기 · 4명`으로 이름을 제안). 타이핑 1회는 탭 1회보다 훨씬 비싸므로, **체감 비용에서는 C가 가장 싸다.**

`ASSUMP-A2-05` — 태그 부여 65탭을 C의 비용으로 계상했다. **이건 C에 불리한 쪽으로 센 것이다**: A/B에서도 사람은 같은 분류를 머릿속에서 매번 꺼내야 하는데 그 비용은 탭으로 안 잡히기 때문이다. C는 그 머릿속 분류를 **한 번 외재화하고 재사용**한다.
`ASSUMP-A2-06` — 제안 정확도 68%(25건 중 8건 수정)는 **근거 없는 잠정치**다. 이 숫자가 C의 전부를 좌우한다(→ 깨지는 조건).

### C-3. N:M(D-02) 표현

- 사람 목록의 행은 A/B와 동일(대표 1개 + 개수 배지).
- **C만의 것**: 제안 그룹 카드 안에서 다른 그룹에도 걸치는 사람 이름 옆에 `겹침` 표식. C에서 겹침은 성가신 예외가 아니라 **제안의 신뢰도가 낮다는 신호**로 읽힌다 — 겹침이 많은 카드일수록 사람이 더 봐야 한다.
- `ref-09`의 칩 붕괴는 여기서도 회피된다. 애초에 그룹 카드가 **모임 쪽에서 사람을 나열**하므로 사람 행에 여러 소속을 우겨넣을 필요가 줄어든다.

### C-4. 미배정 추적(D-03)

C는 **세 숫자를 하나로 합쳐야** 한다. 여기가 C에서 가장 까다로운 지점이다.

- `남은 제안 12건 · 보류 5명 · 어디에도 안 잡힌 사람 3명`
- 이 셋을 **한 줄에 합산해 `아직 정해지지 않은 사람 N명`** 으로 상시 표시하고, 탭하면 세 갈래로 펼친다.
- **제안 카드 큐의 남은 장수 자체가 진척도**다(`ref-10`의 "남은 카드로 잔여를 표현" + `ref-06`의 "숫자 + 상태 서술"). `ref-07`의 `No Status` 동등 취급 원칙에 따라 **보류를 별도 화면에 숨기지 않는다.**
- `ASSUMP-A2-07` — 이 3합산 표시는 우리가 발명한 것이고 실측 근거가 없다(사각지대 1). **세 숫자를 하나로 합치면 "무엇이 남았는지"의 해상도가 떨어질 위험**이 있어, 목업에서 사람이 봐야 할 지점이다.

### C-5. 애매한 사람 · 1:1

- **`ref-10`의 3지선다가 여기 들어간다.** C는 세 후보 중 유일하게 `Same / Different / Not sure`를 **원본 형태 그대로**(한 건씩 묻는 하단 카드 + 3응답) 쓸 수 있는 안이다. 앱이 먼저 움직여야 "물어볼 시점"이 생기기 때문이다.
- 문구 번역: `대학 동기에` / `동네 친구에` / `아직 모르겠다`. **비가역 확인 다이얼로그는 버린다**(`ref-10` "안 가져올 것") — 편성은 언제든 되돌려진다.
- **1:1**: `상사` 태그가 붙은 사람은 앱이 **크기 1 모임**을 제안한다. 카드 형태는 4명짜리와 완전히 동일하고 이름이 1줄일 뿐 → `D-06` 준수. 오히려 C가 1:1을 가장 잘 다룬다(사람이 "이 사람은 따로"를 매번 기억할 필요가 없다).

- **`ASSUMP-A2-06` 정확도.** 제안 정확도가 60% 아래면 수정 비용(8건 → 12건 이상)이 눌러앉아 **수동보다 비싸진다.** 태그 5종으로 만든 교집합이 3~6명을 맞출 확률에 근거가 없다.
- **태그 1종에 15명 넘게 몰리면** 제안 그룹이 3~6명을 못 맞춘다("직장 동료 22명" 같은 덩어리). → 앱이 하위 분할을 물어야 하고, 그건 또 하나의 카드 종류다.
- **제안이 확정처럼 보이면 끝난다**(컨벤션 11). 점선/`제안` 라벨이 축 3의 무드 결정으로 약해지면 이 안 전체가 무너진다 — **축 2가 축 3에 의존하게 되는 유일한 지점**이라 명시해 둔다.

**진단 — 축 분리 실패인가?** 아니다. 셋을 갈라놓은 것(주도권)은 정상적으로 갈렸다. 원인은 다른 데 있다: **축 2의 레퍼런스 5장 중 2장(`ref-07`·`ref-08`)이 규범 문서이고, 나머지 3장은 실측값이 전부 미확보**(`CH-01` 인증 벽)라서 **수치라고 부를 수 있는 것이 M3밖에 없었다.** 즉 축이 아니라 **채널 편중**이 원인이다. `references.md` 사각지대 1·2가 여기서 청구서로 돌아온 것이다.

**벌릴 방법 3가지** (B-3.5 목업에 반영할 것)

1. **M3 값을 그대로 쓰는 것을 후보 A의 정체성으로 고정한다.** A는 "관습 그대로"가 존재 이유이므로 규범값 일치가 오히려 정직하다. 대신 **B와 C는 하단 대역의 구성을 다르게 만든다** — A는 80dp 액션 바(등장/퇴장), B는 80dp 핀 바(**상시 고정**, 4요소 1행), C는 하단 카드 스택(**높이 가변**). 같은 80dp라도 *무엇이 거기 사는가*가 다르면 눈으로 구분된다.
2. **radius·spacing 단계를 축 3에 넘겨서 축 2가 토큰을 정하지 않게 한다.** `layout.uniform-rounding`은 `harness.scaleFloor`로 판정되므로 `DESIGN.md`에서 단계를 만들면 세 후보 모두에서 동시에 해소된다. **축 2 후보 문서가 radius를 언급하지 않는 것이 옳다.**
3. **`motion.missing-micro-interactions`는 지금 못 박는다** — 세 후보 전부 필수: 행 `pressed` 상태 / 부착·확정 성공 시 **카운트 숫자의 변화 자체가 피드백**(별도 토스트를 띄우지 않는다). B는 여기에 `되돌리기` 3초를 추가.

`ASSUMP-A2-08` — 위 1번은 "같은 높이라도 내용이 다르면 구분된다"는 가정이다. 목업 3장을 나란히 놓고 실제로 구분되는지가 B-3.5의 확인 사항.

- **형태**: 앱이 초안 그룹을 만들되 **확정과 구분된 상태**로 두고, 경계 사례만 하단 카드로 **한 건씩** 묻는다. 응답은 **3지선다**(A에 / B에 / **아직 모르겠다**). 보류는 잔여 카운트에 계속 합산된다. **일괄 확정 명령을 만들지 않는다.**
- **성립 조건**: 분류 신호(태그 등)가 항목당 1개 이상 존재 / 제안 정확도 **60% 이상** / 신호 1종당 항목 15명 이하 / 경계 사례가 전체의 10~30% / 최소 폭 **360px**(카드 1장).
- **무너지는 조건**: 신호가 없으면 콜드 스타트로 화면이 빈다. 정확도가 60% 아래면 수정 비용이 수동보다 커진다. 경계 사례가 50%를 넘으면 큐가 곧 전수 검사다. **큐는 끝나는 작업이라, 소진 후 화면의 존재 이유가 사라진다.**
- **대안 패턴**: `PT-01`(행동 큐 — 신호가 상시 재생산될 때), `PT-A2-01`(규칙을 못 만들 때).
- **근거**: 이식 — `ref-10` + Spotify 보조 관찰 + `ref-06`의 rule.

## 6. 추천안

**후보 B(목적지 핀 + 선택 유지)를 추천안으로 본다.** 이유는 탭 수가 가장 적어서(130)가 아니라 — 그 차이는 A와 21%뿐이고 C와는 8%밖에 안 난다 — **이 축에서 우리가 실제로 아는 것과 모르는 것의 경계에 정확히 서 있기 때문**이다. B가 기대는 것은 전부 근거가 있는 메커니즘이다: 상하 분리(`ref-06`), 액션 후 유지(`ref-08`), 부착≠이동(`ref-09`), 보류의 정식화(`ref-10`). 반면 C 전체는 **`ASSUMP-A2-06`(제안 정확도 68%) 하나에 매달려 있고 그 숫자에는 아무 근거가 없다** — 정확도가 60% 밑이면 C는 A보다 비싸지고, 우리는 그게 60% 위인지 아래인지 알 방법이 지금 없다. A는 반대 방향으로 안전하지만 `D-01`을 편성 화면에서 사실상 포기하고, "애매한 사람"(PRD §2-1이 명시한 어려움)을 표현할 자리가 아예 없다 — 즉 A는 **PRD가 어렵다고 말한 것을 안 푸는 안**이다. B는 그 자리에 `보류` 핀을 만들어 `ref-10`의 판단 보류를 수동 동선 안으로 끌고 들어오고, 미배정 카운트가 탭마다 줄어드는 것을 같은 시야에 두어 "165탭짜리 노동"을 "숫자가 줄어드는 일"로 바꾼다. B의 위험은 두 개로 좁혀져 있고 둘 다 목업에서 눈으로 판정된다 — 핀 모드의 오조작 가능성과, 360px에서 핀 바 4요소가 들어가는지. **이 두 개는 그릴 수 있고, C의 정확도 가정은 그릴 수 없다.**

**셋 다 살려서 B-3.5 목업 보드로 넘긴다.** 세 안이 같은 화면·같은 데이터(55명 / 25모임 / 미배정 12명)로 그려졌을 때 눈에 보이는 차이는 **하단 80dp 대역에 무엇이 사는가** 하나로 요약된다 — A는 선택했을 때만 나타나는 액션 바, B는 목적지와 카운트가 상주하는 핀 바, C는 높이가 변하는 제안 카드 스택. 최종 선택은 사람이 한다.

### A. 모바일 다중선택 + 일괄 액션 바

| 항목 | 값 | 근거 |
|---|---|---|
| 선택 개수 표시 위치 | **상단 앱바 제목 자리** (좌측 X = 선택 해제, 우측 = 일괄 액션). 선택이 시작되면 기존 앱바가 컨텍스추얼 앱바로 **치환**됨 | ref-02, ref-01 |
| 상단 앱바 높이 | **64dp** (M3 standard top app bar). 좌우 콘텐츠 패딩 24dp, 아이콘 상하 패딩 20dp | ref-02 (M3 app-bars specs, 2차 출처) |
| 일괄 액션이 붙는 대역 | **화면 하단** — 바텀 액션 바 또는 슬라이드업 바텀시트. 선택 대상과 시각적으로 가깝게 | ref-01, CH-03 공통 |
| 하단 액션 바 높이 | **80dp** (M3 bottom app bar container height) | ref-02 (2차 출처) |
| 리스트 행 높이 | 1줄 **56dp** / 2줄 **72dp** / 3줄 **88dp** | ref-02 (2차 출처) |
| 체크박스 | 시각 지표 **40×40dp**, 터치 타깃 **48×48dp**, 타깃 간 간격 **8dp 이상** | ref-02 |
| 수평 패딩 | 리딩 아이콘 좌측 **16dp**, 텍스트 시작 **72dp**, 우측 **16dp** | ref-02 (2차 출처) |
| 개수 라벨 문구 | `N selected` / `Select page` / `Select all` / `Select none` | ref-03 |

**우리 제약에서의 결론**: 개수+해제는 상단(64dp), 실행은 하단(80dp)로 **상하 분리**. M3는 일괄 액션도 상단에 두지만, 390px 한 손 조작에서 상단 우측은 엄지 사각지대라 그대로 쓰면 안 됩니다.
390px 폭 계산: 좌측 패딩 16 + 체크박스 터치 48 + 텍스트 시작 72dp 기준 → 텍스트 가용 폭 약 **302px**. 여기에 소속 모임 표시까지 얹으려면 행은 최소 2줄(72dp)이어야 합니다.

### ref-02 · Material Design 3 — Selection mode / Contextual top app bar · [축 2]
- 채널: CH-04 | 출처: https://m3.material.io/foundations/interaction/selection , https://m3.material.io/components/app-bars/specs , 수치 2차 출처 https://github.com/material-components/material-components-android/blob/master/docs/components/List.md , https://developer.android.com/develop/ui/compose/accessibility/api-defaults

- 메커니즘: 선택이 시작되면 상단 앱바가 **컨텍스추얼 앱바로 치환** — 제목 자리에 선택 개수, 좌측에 X(선택 해제), 우측에 일괄 액션. 항목 행에는 리딩 체크박스가 나타남. 즉 **선택 개수와 탈출구가 같은 대역에 붙는다.**

- 안 가져올 것: 액션 아이콘만 늘어놓는 상단 오버플로 메뉴(⋮) — 우리 액션은 "모임에 추가"라는 **목적지 선택**이지 아이콘화되는 동사가 아님.
- 실측값: 상단 앱바 **64dp**(좌우 콘텐츠 패딩 24dp, 아이콘 상하 패딩 20dp), 하단 앱바 컨테이너 **80dp**. 리스트 행 1줄 **56dp** / 2줄 **72dp** / 3줄 **88dp**. 리딩 아이콘 좌측 패딩 16dp, 텍스트 시작 72dp, 우측 패딩 16dp. 체크박스 시각 지표 **40×40dp**, 터치 타깃 **48×48dp**, 타깃 간 최소 간격 **8dp**.
- 종류 수: 행 높이 3종(56/72/88), 수평 패딩 실질 2종(16/72), 앱바 높이 2종(64/80)
- 모바일 성립 여부: 성립 — 390px에서 좌측 체크박스 48 + 텍스트 영역 ~302 + 우측 여백이 정확히 들어감. 단 행에 소속 표시까지 얹으려면 2줄(72dp) 이상 필요.

### ref-03 · PatternFly — Bulk selection · [축 2]
- 채널: CH-04 | 출처: https://www.patternfly.org/patterns/bulk-selection/
- 도메인 관계: 타도메인(같은 job: 대량 목록에서 부분집합을 만들고 일괄 처리 — 엔터프라이즈 데이터 테이블)
- 해결한 문제: 목록이 화면보다 길 때 "내가 지금 몇 개를, 어디까지 골랐는가"의 혼동
- 메커니즘: 툴바 첫 항목에 **체크박스+드롭다운 분할 버튼**. **3상태 체크박스**(빈칸 / 부분선택=마이너스 / 전체=체크). 드롭다운은 `Select page`(현재 화면분) vs `Select all`(전체) vs `Select none`을 **명시적으로 구분**하고, 개수 라벨은 페이지 경계를 넘어 총합을 표시. 결정적: **액션을 실행한 뒤에도 선택 상태가 유지**되고, 사용자가 의도적으로 바꿀 때만 풀린다.
- 이식 가능성: 가능 — "액션 후 선택 유지"가 우리에게 핵심. 한 사람이 여러 모임에 속하므로 **모임 A에 넣은 직후 같은 선택을 모임 B에도 넣는** 연속 동작이 자연스럽게 나옴. 커버링 문제에 정확히 맞는 메커니즘.
- 안 가져올 것: 분할 버튼(드롭다운) 형태 — 데스크톱 툴바 위젯이라 390px에서 히트 타깃이 두 개로 쪼개져 오탭. 필터 결과 전체 선택은 버튼 하나로.
- 실측값: 수치 없는 문서. 라벨 문구는 확보 — `Select page` / `Select all` / `Select none` / `N selected`.
- 종류 수: 체크박스 상태 3종
- 모바일 성립 여부: 조건부 — 3상태 체크박스와 "액션 후 선택 유지"는 성립, 분할 버튼은 불가.

### ref-04 · Gmail — 라벨(N:M 소속) · [축 2]
- 채널: CH-03 | 출처: https://zapier.com/blog/gmail-labels/ , https://support.google.com/mail/answer/118708?hl=en&co=GENIE.Platform%3DAndroid
- 도메인 관계: 타도메인(같은 job: 한 항목이 여러 그룹에 동시 소속 — 폴더가 아닌 라벨 모델)
- 해결한 문제: "이동"이 아니라 "부착"이라는 것을 사용자가 오해 없이 알게 하기
- 메커니즘: 라벨은 **폴더가 아니라 태그**여서 하나의 메일에 여러 개가 붙고, 붙여도 원 위치에서 사라지지 않음. 목록 행에서는 제목 옆에 **컬러 칩**으로 붙은 라벨을 노출. 라벨을 누르면 그 라벨이 붙은 항목만 걸러진 뷰가 열리는데, 이는 **필터일 뿐 이동이 아님.**
- 이식 가능성: 조건부 — "부착 모델"은 우리 커버링 구조 그 자체라 개념적으로 완전 일치. 다만 **칩 표시 한계가 우리 규모에서 먼저 터짐**: 한 사람이 3~4개 모임에 걸치면 390px 행에서 칩이 잘리고, 잘린 칩은 누락 감지에 아무 도움이 안 됨.
- 안 가져올 것: 색으로 그룹을 구분하는 방식 — 모임 20~30개에 색 20~30종은 구분 불가이고 목록이 무지개가 됨(AI 슬롭). 칩 대신 **개수 배지("3개 모임")**로 축약하고 상세는 탭 시 펼치는 쪽이 우리 규모에 맞음.
- 실측값: **미확보** — 모바일 라벨 칩의 최대 표시 개수/말줄임 규칙은 텍스트 문서에 없고 스크린샷이 필요(사각지대 2번).
- 종류 수: 미확보
- 모바일 성립 여부: 조건부 — 소속 수 1~2개일 때만 칩이 성립. 3개 이상은 불가.

### ref-05 · Google Photos — 얼굴 그룹 병합 제안 · [축 2]
- 채널: CH-03 | 출처: https://support.google.com/photos/answer/6128838?hl=en-GB&co=GENIE.Platform%3DiOS , https://www.androidpolice.com/2018/07/28/google-photos-web-starts-suggesting-merge-faces-person/
- 도메인 관계: 타도메인(같은 job: 앱이 먼저 자동 그룹을 만들고 사람이 검수·수정 — 애매한 항목 처리 포함)
- 해결한 문제: 자동 그룹핑이 틀릴 수 있을 때 사용자에게 **되돌릴 수 없는 결정**을 어떻게 받을 것인가
- 메커니즘: 앱이 먼저 그룹을 만들고, **확신이 낮은 경계 사례만** 카드 형태로 하단에서 **한 건씩** 물어봄. 응답이 2지선다가 아니라 **3지선다 — `Same` / `Different` / `Not sure`**. 즉 "판단 보류"를 정식 응답으로 인정해서 애매한 항목이 강제로 어느 한쪽에 들어가는 것을 막는다. 병합은 비가역이라고 명시하고 그래서 확인 단계를 둔다.
- 이식 가능성: 가능 — 우리 최대 실패 비용(누락)과 구조가 같음. 제안이 애매한 사람(대학 동기 ∩ 동네 친구, 또는 1:1로 만나야 하는 상사)을 임의로 밀어넣지 않고 **"보류" 상태로 남겨 미분류 카운트에 계속 잡히게** 하는 설계의 근거. 카드 한 건씩 = 390px에 그대로 맞음.
- 안 가져올 것: 병합의 **비가역성** — 우리는 모임 편성이 언제든 되돌려져야 함(사회적 비용이 큰 건 누락이지 재편성이 아님). "취소할 수 없습니다" 확인 다이얼로그는 버림.
- 실측값: 미확보. 구조적 사실 — 제안 카드는 하단에서 뜨고, 한 번에 한 건, 응답 3종.
- 종류 수: 응답 상태 3종
- 모바일 성립 여부: 성립

### ref-06 · QuickBooks Online / 모바일 — `For review` 카운트 · [축 2]
- 채널: CH-03 | 출처: https://quickbooks.intuit.com/learn-support/en-ca/help-article/banking/categorize-match-online-bank-transactions-online/L1bTafTz3_CA_en_CA , https://quickbooks.intuit.com/learn-support/en-us/banking/when-we-see-37-to-review-have-these-transactions-already-been/00/224786
- 도메인 관계: 타도메인(같은 job: 자동으로 들어온 항목을 사람이 하나씩 분류해 0으로 만드는 작업)
- 해결한 문제: "아직 처리 안 된 것이 몇 개 남았는가"를 사용자가 매번 찾아 들어가지 않아도 알게 하기
- 메커니즘: 미분류 항목은 `For review` **탭에 격리**되고, 개수가 **Banking 탭의 계좌 타일 안에 잔액과 나란히** 상시 표시(`"37 to Review"`). 결정적으로 **그 항목들은 아직 장부에 반영되지 않은 상태**임을 명시 — 카운트가 단순 숫자가 아니라 "미완료 상태"를 뜻함. 각 항목에서 사람은 `Match`(기존 것과 연결) 또는 `Categorize`(새로 분류) 중 선택. 반복되는 것은 규칙(rule)으로 만들어 이후 자동 분류.
- 이식 가능성: 가능 — `아직 어느 모임에도 없는 사람 N명`으로 그대로 번역됨. "숫자 + 상태 서술"이 핵심(그냥 `12`가 아니라 `12명 미배정`). 규칙 = 우리 쪽 태그 기반 자동 그룹핑의 근거.
- 안 가져올 것: 미분류를 **별도 탭에 격리**하는 것 — 탭을 열어야만 보이면 누락을 놓친다. 우리는 카운트가 메인 화면에 상시 떠 있어야 함. 또 `Match`/`Categorize` 이중 동사 구조는 우리에게 대응물이 없음.
- 실측값: 미확보(수치 없는 헬프 문서). 구조적 사실 — 카운트 위치 2곳(계좌 타일 안 + 탭 라벨), 문구 형태 `N to Review`.
- 종류 수: 미확보
- 모바일 성립 여부: 성립 (모바일 앱에 동일 흐름이 있다고 문서에 명시)

### ref-07 · Notion 보드 뷰 — 그룹 헤더 카운트 / `No Status` 컬럼 · [축 2]
- 채널: CH-03 | 출처: https://www.notion.com/help/boards , https://www.notion.vip/insights/the-grouping-guide
- 도메인 관계: 타도메인(같은 job: 항목을 그룹으로 편성하고, 어디에도 안 들어간 것을 눈에 보이게 두기)
- 해결한 문제: 그룹핑 뷰에서 "값이 없는 항목"이 조용히 사라지는 것을 막기
- 메커니즘: 각 **그룹 컬럼 헤더 바로 우측에 회색 숫자**로 카드 수를 상시 노출. 그룹 속성 값이 없는 항목은 **`No Status`라는 전용 그룹 컬럼**에 모여 다른 그룹과 **동등한 지위로** 표시되고 같은 방식으로 카운트됨. 즉 미분류가 특별한 오류 상태가 아니라 **하나의 그룹**으로 다뤄진다. 컬럼 숨김/표시는 Group 설정에서 제어.
- 이식 가능성: 조건부 — "미분류를 하나의 그룹으로 동등 취급 + 헤더에 카운트"는 그대로 가져올 만함. 다만 **가로 스크롤 칸반은 390px에서 불가** — 20~30개 모임이 옆으로 늘어서면 미분류 컬럼이 화면 밖으로 밀려나 목적을 잃는다. 세로 섹션 리스트로 바꾸고 **미분류 섹션을 맨 위에 고정**해야 성립.
- 안 가져올 것: 가로 스크롤 보드 레이아웃, 그룹 컬럼 숨김 기능(미분류를 숨길 수 있으면 안 됨 — 누락 방지와 정면 충돌).
- 실측값: 미확보(수치 없는 헬프 문서). 구조적 사실 — 카운트는 그룹 헤더 우측, 회색 숫자.
- 종류 수: 미확보
- 모바일 성립 여부: 조건부 — 카운트 배치는 성립, 가로 보드 레이아웃은 불가.

## 컨벤션 목록 (어기면 사용자가 헤맨다)

1. **선택 개수와 선택 해제(X)는 같은 대역에 붙는다** — 상단 컨텍스추얼 앱바. 개수만 있고 탈출구가 없으면 갇힌 느낌이 난다. (ref-02, ref-01)
2. **일괄 액션은 선택된 항목 근처/하단에 붙는다** — 액션 바가 선택 대상과 시각적으로 멀거나 끊겨 보이면 사용자가 실행을 주저한다. (ref-01, CH-03 공통 서술)
3. **부분 선택은 빈칸도 체크도 아닌 제3의 상태(마이너스)로 표시한다** — 이 상태 없이 전체 선택 체크박스를 만들면 "전체가 선택됐다"고 오독한다. (ref-03)
4. **"이 화면 전체 선택"과 "전부 선택"은 다른 명령으로 분리한다** — 하나로 합치면 사용자가 자기가 뭘 골랐는지 모른다. (ref-03)
5. **터치 타깃 48dp, 타깃 간 8dp 이상** — 체크박스 시각 지표가 40dp라도 히트 영역은 48dp. 행에서 체크박스 탭과 행 탭(상세 열기)이 겹치면 오탭이 상시 발생. (ref-02)
6. **라벨/태그 부착은 "이동"으로 보이면 안 된다** — 부착 후에도 원 목록에 남아 있어야 N:M 모델이 이해된다. (ref-04)
7. **자동 제안은 확정 상태와 시각적으로 구분된 상태로 존재한다** — 제안이 이미 확정처럼 보이면 사람이 검수를 건너뛴다. (Spotify 보조 관찰, ref-05)
8. **미분류 카운트는 숫자만이 아니라 상태 서술을 동반한다** — `37`이 아니라 `37 to Review`. 숫자만으로는 그것이 좋은 건지 나쁜 건지 모른다. (ref-06)
9. **미분류는 특별 취급된 오류가 아니라 하나의 그룹으로 목록에 존재한다** — 별도 화면으로 격리하면 안 열어보고, 안 열어보면 누락된다. (ref-07, ref-06의 반례)

## 기대했는데 안 나온 것 (= 채널 사각지대)

1. **픽셀 단위 실측값 전반이 CH-04 규범 문서에만 의존.** ref-01·03·04·05·06·07 여섯 장이 전부 `실측값 미확보`입니다. 실제 제품이 규범값을 얼마나 따르는지, 국내 앱의 관행 값은 얼마인지는 **CH-01 uibowl 인증이 열려야만** 확인 가능합니다. 현재 신뢰할 수 있는 수치는 M3 계열(56/72/88dp, 48dp, 64dp, 80dp, 16/72dp)뿐입니다.
2. **N:M 소속의 목록 내 표시 한계치**(칩을 몇 개까지 보여주고 초과분을 어떻게 줄이는가 — `+2` 배지인지 말줄임인지)에 대한 근거 **없음**. Gmail 모바일의 칩 말줄임 규칙은 텍스트 문서에 안 적혀 있고 스크린샷이 필요합니다. 우리 규모(한 사람이 3~4개 모임)에서 가장 먼저 터지는 지점인데 근거가 비어 있습니다.
3. **CH-04의 원본 두 곳(Apple HIG, M3 lists specs) 본문이 WebFetch로 안 열림.** 2차 출처로 우회한 수치는 신뢰 가능하지만, **컨텍스추얼 앱바 자체의 내부 패딩·개수 텍스트 타입 스케일**은 미확보입니다.

5. **자도메인(웨딩/청첩장) 레퍼런스 0건** — 의도적으로 안 찾았습니다. 축 2에서 자도메인 대조가 필요하면 별도 지시가 필요합니다.

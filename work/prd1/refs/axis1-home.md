# B-2 레퍼런스 소싱 — 축 1: 홈의 조직 원리

**축 정의:** 수십 건의 진행 중인 조율을 앱이 무엇을 기준으로 조직해 보여주는가.
양 끝: `행동 큐`(지금 할 일만) ↔ `상태 보드`(단계별 칸) ↔ `캘린더`(시간 축)

**채널 상태:** CH-01(uibowl MCP)은 OAuth 인증 벽에 막힘 — 우회하지 않음. CH-03(웹 검색/큐레이션), CH-04(디자인 시스템 문서), 로그인 없이 공개된 제품 문서(CH-02 범위 내)로 진행.

## 메커니즘 카드

### ref-01 · Linear — My Issues · [축 1]
- 채널: CH-03 / 제품 공식 문서 | 출처: https://linear.app/docs/my-issues
- 도메인 관계: 타도메인(같은 job: 수십~수백 건의 진행 중 항목 중 "내가 지금 손대야 할 것"만 골라내기)
- 해결한 문제: 보드(상태 칸)는 전체 파이프라인을 보여주지만 "지금 뭐부터"를 답하지 못한다.
- 메커니즘: 보드와 **별개의 뷰**로 행동 큐를 두고, 그 큐를 **긴급도 카테고리로 섹션 분할**해 정렬한다. 문서가 명시한 순서: `urgent work → SLA-bound work → blockers → cycle work → other active work → triage → backlog → completed`. 섹션 내부는 우선순위 정렬 + 시작된 항목 우선. 워크스페이스에 해당 항목이 없으면 **그 섹션 자체가 사라진다**(빈 섹션 헤더를 남기지 않음).
- 이식 가능성: 가능 — 우리 행동 신호 3종(회신 마감 도래 / 며칠째 무응답 / 날짜 충돌)이 그대로 `urgent → SLA-bound → blockers` 자리에 대응된다. "섹션이 비면 사라진다"는 규칙은 20~30건 규모에서 스크롤 낭비를 없애는 핵심.
- 안 가져올 것: 8개 섹션 전부. 우리는 신호가 3종이므로 섹션도 3~4개가 상한이다. 또한 `created by me / subscribed / activity` 4탭 구조 — 우리 사용자는 1명이고 전부 자기가 만든 것이라 탭이 무의미하다.
- 실측값: 섹션 8종(상한), 섹션 내 2단 정렬 규칙(우선순위 → 시작 여부). 픽셀 수치는 문서에 없음.
- 종류 수: 문서에서 확인 불가.
- 모바일 성립 여부: 조건부 — 리스트/보드 토글은 모바일에도 있으나, 보드는 360px에서 한 칸만 보이므로 실질 기본은 리스트.

### ref-02 · Airbnb 호스트 Today 탭 · [축 1]
- 채널: CH-03 / 제품 공식 리소스 | 출처: https://www.airbnb.com/resources/hosting-homes/a/reservations-redesigned-765 , https://www.rentalscaleup.com/what-airbnbs-new-today-host-tab-and-price-comparison-tool-with-booking-com-say-the-companys-priorities/
- 도메인 관계: 타도메인(같은 job: 수십 건의 동시 진행 예약을 **마감 있는 회신 압박**과 함께 조율)
- 해결한 문제: 예약은 시간축(캘린더)에 있지만, 놓치면 안 되는 것은 "24시간 내 수락/거절"처럼 **시간축 위가 아니라 큐에 있는 것**이다.
- 메커니즘: 홈을 **2층 구조**로 쪼갠다. 상단 = 응답 요구 섹션(예약 요청 카드 + 수락/거절 버튼 + **24시간 카운트다운 타이머**), 하단 = 시간순 예약 목록. 즉 행동 큐를 캘린더 위에 얹었지, 둘 중 하나를 고르지 않았다. 개별 알림(스마트락 끊김 등)은 별도 알림 탭이 아니라 **해당 예약 카드 안에** 붙는다.
- 이식 가능성: 가능 — 우리의 "회신 마감 도래"가 정확히 카운트다운 슬롯이다. 홈 = `행동 필요 큐(상단) + 다가오는 모임(하단, 시간순)` 하이브리드가 우리 제약(마감 고정 + 행동 누락이 치명)과 맞는다.
- 안 가져올 것: 카드 안의 정보 밀도(수익 내역, 취소 정책, 게스트 평점, 메시지/전화 버튼). 호스트는 1회 수 분을 쓰지만 우리 사용자는 **1회 수십 초**다. 카드가 아니라 한 줄이어야 한다.
- 실측값: 응답 마감 24시간 = 카운트다운을 붙이는 임계. 홈 섹션 2개.
- 종류 수: 확인 불가.
- 모바일 성립 여부: 성립 — 원래 모바일 앱 기준 설계.

### ref-03 · Todoist — Today 뷰 · [축 1]
- 채널: CH-03 / 제품 공식 도움말 | 출처: https://www.todoist.com/help/articles/plan-your-day-with-the-todoist-today-view-UVUXaiSs
- 도메인 관계: 타도메인(같은 job: 여러 프로젝트에 흩어진 항목 중 오늘치만 한 리스트로)
- 해결한 문제: 프로젝트(=상태 보드)별로 나뉜 항목을 매번 순회하지 않고 한 뷰에서 소화.
- 메커니즘: **"날짜가 있는 것만 Today에 뜬다"** — 큐에 들어오는 자격 조건을 날짜 하나로 단일화. 날짜 없는 항목은 큐에 아예 나타나지 않는다. 최우선(P1) 항목은 리스트 최상단에 색으로 분리. 같은 데이터에 리스트/캘린더 레이아웃을 토글, 캘린더 레이아웃에서는 사이드 패널에 overdue/종일 항목을 따로 뺀다(캘린더 격자에 놓을 자리가 없는 것들). 밀린 항목은 드래그로 내일로 미룸.
- 이식 가능성: 조건부 — "큐 진입 자격을 단일 조건으로 정의한다"는 규칙은 그대로 가져올 만하다(우리: 행동 신호 3종 중 하나라도 켜진 모임만 큐에 뜬다). 다만 **미루기(postpone)는 우리에게 위험하다** — 예식일이 고정이라 미루기가 행동 누락으로 직결된다.
- 안 가져올 것: 드래그로 내일 미루기, 사용자가 정렬/그룹핑을 직접 설정하는 옵션. 1회 수십 초 사용자에게 뷰 설정 학습 비용은 과하다 — 정렬은 앱이 정해줘야 한다.
- 실측값: 큐 진입 조건 = 1개. 강조 등급 = 1개(P1만 색 분리).
- 종류 수: 확인 불가.
- 모바일 성립 여부: 성립(리스트). 캘린더 레이아웃은 조건부 — overdue를 격자 밖 별도 패널로 빼야만 성립한다는 것이 이 레퍼런스의 관찰점.

### ref-04 · Material Design 3 — Lists · [축 1]
- 채널: CH-04 | 출처: https://m3.material.io/components/lists , https://m1.material.io/components/lists.html (수치 원문)
- 도메인 관계: 타도메인 — 컨벤션·수치 근거
- 해결한 문제: "원인 + 다음 행동"을 한 줄에 담을 때 몇 줄까지가 리스트 아이템인가.
- 메커니즘: 행 높이를 **줄 수로만** 규정한다. 1줄 56dp / 2줄 72dp / 3줄 88dp. 좌우 패딩 16dp, 아바타·아이콘이 있으면 텍스트 시작선 72dp. 리스트 상하 8dp. 3줄 아이템은 상 16 / 하 20dp. 즉 **3줄이 리스트 아이템의 상한**이고 그 이상은 카드로 넘어간다.
- 이식 가능성: 가능 — 우리 한 줄의 예산이 여기서 결정된다. 390px 폭에서 리딩 아이콘(상태) 자리를 쓰면 텍스트 가용폭은 약 390 − 72 − 16 = **302px**. 여기에 모임명(줄1) + 원인 문구(줄2)까지가 2줄 72dp. 다음 행동을 텍스트로 3줄째에 넣으면 88dp가 되고 한 화면 노출이 급감하므로, **행동은 트레일링 버튼/셰브런으로 밀어내는 편**이 예산에 맞는다.
- 안 가져올 것: 3줄 레이아웃. 20줄 과밀 시 88dp × 20 = 1760dp로 스크롤이 길어진다.
- 실측값: 56 / 72 / 88dp, 패딩 16dp, 텍스트 시작 72dp, 리스트 상하 8dp. iOS 최소 터치 타깃 44pt와 겹쳐 보면 56dp(1줄)가 하한선.
- 종류 수: 행 높이 3종 / 패딩 3종(8, 16, 72) — 리스트 한정.
- 모바일 성립 여부: 성립 (360px 기준으로 정의된 스펙).

### ref-05 · 플랜잇웨딩 (국내 결혼 준비 앱) · [축 1]
- 채널: CH-03 | 출처: https://apps.apple.com/kr/app/id6744094799 , https://apps.apple.com/us/app/id994071144 (웨딩북)
- 도메인 관계: **자도메인**
- 해결한 문제: 결혼 준비의 다항목 진행 상황을 하나의 홈에 요약.
- 메커니즘: 홈의 조직 축이 **D-day(마감까지 남은 일수) + 단계별 체크리스트 + 예산**이다. 즉 조직 원리가 "행동 큐"가 아니라 **진척률 대시보드**다. 캘린더는 별도 뷰로, 날짜에 항목과 지출을 등록하는 기록용. 웨딩북도 동일하게 홈 최상단 D-day + 카테고리 탭(웨딩홀/스드메 등) 구조.
- 이식 가능성: **조건부** — D-day는 가져올 것(예식일 고정이 우리 제약의 핵심이고, 자도메인 사용자가 첫 화면에서 기대하는 것). 그러나 체크리스트/진척률은 **우리 문제를 풀지 못한다**: 자도메인 앱들의 항목은 순차적 준비 단계(수십 건 동시 진행 아님)이고, 회신을 기다리는 비동기 대기 상태가 없다.
- 안 가져올 것: 진척률 게이지/퍼센트를 홈의 주 조직 원리로 삼는 것. 20~30건이 각기 다른 5~6개 상태에 흩어져 있을 때 "68% 완료"는 **다음 행동을 하나도 알려주지 않는다** — 우리 실패 모드(행동 누락)를 정면으로 놓친다. 카테고리 탭 구조도 제외(우리는 카테고리가 아니라 상태로 갈린다).
- 실측값: 홈 최상단 고정 요소 1개(D-day). 카테고리 탭 4~6개.
- 종류 수: 확인 불가(스토어 설명 기반, 스크린샷 실측 못 함).
- 모바일 성립 여부: 성립.

## 컨벤션 목록 (자도메인 기준 — 어기면 사용자가 헤맴)

1. **홈 최상단에 D-day가 고정으로 있다** — 근거 ref-05(플랜잇웨딩, 웨딩북 공통). 예식일 고정이라는 제약을 사용자가 항상 의식하고 있고, 이게 없으면 "이 앱이 내 결혼 준비를 알고 있나"라는 신뢰가 깨진다.
2. **준비 항목은 단계(스테이지)로 이름 붙어 있다** — 근거 ref-05. 우리 상태 5~6종에 임의 라벨을 붙이기보다 자도메인 어휘(예: 미연락 / 회신대기 / 날짜조율중 / 확정 / 전달완료)로 맞추는 편이 학습 비용이 낮다.
3. **예산·비용이 홈 요소로 기대된다** — 근거 ref-05(두 앱 모두). 다만 우리 job은 편성/조율이지 지출 관리가 아니므로, **이건 컨벤션이지만 의도적으로 어겨야 할 후보**다(어겼을 때의 사용자 혼란을 감수할지가 판단 지점).

## 기대했는데 안 나온 것 (= 채널 사각지대)

1. **"몇 건부터 무너지는가"의 수치 근거 — 어디에서도 안 나옴.** 큐/보드/캘린더가 몇 건에서 각각 한계에 부딪히는지 명시한 자료를 찾지 못함. 제품 문서는 자기 방식을 설명할 뿐 한계를 쓰지 않고, 큐레이션 갤러리는 애초에 건수를 안 보여줌. → **A단계(구조 검증)에서 20건·30건 더미 데이터로 직접 재봐야 하는 항목.** 소싱으로는 못 메움.
2. **빈 상태(0건)와 과밀 상태(20줄) — 예상대로 구조적으로 안 나옴.** 갤러리는 베스트 컷 편향이고, 제품 도움말 문서마저 빈 상태 문구를 안 씀(Todoist는 "Todoist Zero"라는 개념어만 언급, 실제 화면 설명 없음). 유일하게 건진 것은 **ref-01의 "해당 섹션이 없으면 섹션 자체가 사라진다"** 규칙 하나 — 이게 과밀·희소 양방향을 동시에 다루는 유일한 구조적 근거. NN/g 빈 상태 문서(https://www.nngroup.com/articles/empty-state-interface-design/)는 원칙 3가지(시스템 상태 전달 / 학습 단서 / 다음 행동 링크)를 주지만 **최초 사용 빈 상태와 "다 처리해서 비었다" 상태를 구분하지 않음** — 우리한테는 이 구분이 핵심인데(0건이 "할 일 없음"인지 "아직 시작 안 함"인지) 그 근거가 공백.
3. **회신 대기(비동기 무응답)를 홈에 어떻게 표현하는가.** ref-02의 24시간 카운트다운이 가장 가까웠지만, 그건 *내가* 응답할 마감이고 우리의 "며칠째 무응답"은 *상대가* 응답하지 않는 상태. 이 신호를 한 줄에 어떻게 담는지의 선례를 못 찾음.
4. **자도메인 레퍼런스가 축 1에 대해 거의 무력했음.** 국내 웨딩 앱들은 전부 진척률 대시보드 모델이라 "수십 건 동시 조율"이라는 우리 job 자체를 다루지 않음. 축 1의 실질 근거는 전부 타도메인에서 나왔고, 자도메인은 **컨벤션(D-day 위치, 단계 어휘)의 근거로만** 사용 가능.

## 소싱 결론 (축 1 한정)

세 레퍼런스가 서로 다른 도메인에서 같은 답으로 수렴함: **행동 큐 / 상태 보드 / 캘린더는 택일이 아니라 층위**다. ref-01은 보드 옆에 큐를 따로 뒀고, ref-02는 큐를 시간순 목록 위에 얹었고, ref-03은 같은 데이터에 레이아웃을 토글하되 캘린더에서 놓칠 항목을 격자 밖으로 뺐다. 세 경우 모두 **행동 큐가 홈이고, 나머지는 부차 뷰**다. 우리 실패 모드가 행동 누락(비가역·사회적)이라는 점을 감안하면 이 수렴은 채택 근거로 강하다 — 다만 위 사각지대 1번(건수 임계)이 미해결이므로 A단계 검증 대상으로 남긴다.

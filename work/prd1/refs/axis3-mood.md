# 축 3 — 비주얼 무드 · 레퍼런스 소싱 보고

**축 정의**: 정서적 도메인(결혼)인데 실제 작업은 운영·조율이다. 화면이 어느 쪽 얼굴을 하는가.
**양 끝**: `운영 도구`(밀도 높고 상태가 주인공) ↔ `예식 정서`(여백 넓고 정서가 주인공)

**제품 맥락**: 청첩장모임 스케줄러 모바일 앱(390px). 지인 40~60명을 20~30개 모임으로 묶고 날짜 조율. 결혼식 3개월 전~2주 전, 주 수회·1회 수십 초. 회신 확인이 주 목적.

**소싱 범위**: 메커니즘 카드 5장 / 채널 2종(CH-03, CH-04) / 출처 8개 / 타도메인 4개.

## 채널 접근 결과

- **CH-01 uibowl — 접근 실패(OAuth 인증 벽)**. `mcp__uibowl__authenticate`가 사용자 브라우저 OAuth URL을 반환. **우회하지 않고 중단**. 결과적으로 "한국어 화면의 실측 타이포"의 1순위 채널이 비었고, 그 공백을 CH-04(KRDS 정부 디자인시스템)로 메웠다. KRDS는 실제 앱 화면이 아니라 규범 문서라서, 국내 상업 앱의 실제 관행(예: 토스·당근의 본문 15px 관행)은 **여전히 미확인**. uibowl 인증이 열리면 이 한 가지는 재소싱 권장.
- **CH-04 접근 성공 2건**(KRDS, Radix/Tailwind), **부분 실패 2건**: Apple HIG typography · Material 3 lists specs는 JS 렌더링이라 WebFetch로 본문 미취득. 2회 시도 후 포기.
- **CH-03 부분 성공**. screensdesign의 Huckleberry 페이지는 스크린샷만 있고 토큰/실측값 없음. Linear는 서드파티 토큰 추출 문서로 실측값 확보.
- **CH-02 실서비스 미사용**(웨딩 앱 대부분 로그인 벽).

### ref-01 · KRDS (대한민국 정부 디자인시스템) · [축 3]
- **채널**: CH-04 | **출처**: https://www.krds.go.kr/html/site/style/style_03.html
- **도메인 관계**: 타도메인 (같은 job: 한국어 고밀도 정보를 '즐기려'가 아니라 '확인하려' 여는 화면에서 정확히 읽히게 하기)
- **해결한 문제**: 한글 본문이 라틴 기준 크기·행간을 그대로 쓰면 무너지는 문제
- **메커니즘**: 본문을 17px/150%로 고정하고, 위계를 크기가 아니라 weight 2종(400/700)으로 만든다. 자간은 본문 0px, 크기 종류는 6종뿐
- **이식 가능성**: 가능 — 우리도 한국어·모바일·정보확인형이라 전제가 거의 동일
- **안 가져올 것**: Pretendard **GOV** 서체(정부 전용 변형, 관공서 인상). 일반 Pretendard로 대체
- **실측값**:
  - body-large-bold 19px / 150% / w700
  - **body-medium 17px / 150%(=25.5px) / w400** ← 기본 본문
  - body-small 15px / 150% / w400, small-bold 15px / 150% / w700
  - body-xsmall 13px / 150% / w400, xsmall-bold 13px / 150% / w700
  - 본문 letter-spacing **0px**
  - 본문 대비율 최소 **4.5:1** (WCAG AA)
  - rem 기준 10px(62.5%)
  - PC/모바일 크기 **동일** (17px이 모바일에서도 17px)
- **종류 수**: 글자 크기 4종(13/15/17/19) × weight 2종 = 토큰 6종 / 행간 **1종**(150% 전 단계 동일) / weight 2종(400·700)
- **모바일 성립 여부**: 성립 (390px에서 그대로 사용)

> **핵심**: 행간을 한 종류(150%)로 고정했다. 행간을 다양화하지 않고 하나로 밀면 고밀도 리스트에서도 줄 리듬이 깨지지 않는다. 축 3에서 "여백 넓음"을 만들 때 **행간이 아니라 블록 간 간격**으로 만들어야 한다는 근거.

**warm vs cool의 실제 손익 (측정된 것)**

차이는 색상(hue)이 아니라 **채도량(chroma)** 이다.

| | 200 단계 chroma | 400 단계 chroma | 500 단계 chroma |
|---|---|---|---|
| stone (warm) | 0.003 | 0.010 | 0.013 |
| slate (cool) | 0.013 | 0.040 | 0.046 |

cool gray는 중간 단계에서 warm의 **3~4배 채도**를 실어 나른다.
- **cool이 얻는 것**: 파란 기운 자체가 "디지털 도구" 신호가 되고, 보조 텍스트(`#64748B`)가 이미 약한 색을 가지므로 액센트 없이도 화면이 심심하지 않다.
- **cool이 잃는 것**: 그 파란 기운이 액센트색과 **경쟁**한다.
- **warm이 얻는 것**: 400~500 단계가 거의 무채색이라 액센트 1색이 화면에서 **유일한 색**이 된다. 배경 `#FAFAF9` 위에서 카드 `#FFFFFF`가 순백으로 떠오른다(cool 배경 `#F8FAFC` 위에서는 같은 흰 카드가 덜 분리됨).
- **결론(관측)**: 정서를 액센트 1색에만 좁혀 넣으려면 warm 쪽이 유리하다.

- **종류 수**: 뉴트럴 단계 12종(Radix 규범) / **우리 권장 5종**(1·2·6·11·12)
- **모바일 성립 여부**: 성립

### ref-04 · Nara Baby vs Huckleberry (육아 기록) · [축 3]
- **채널**: CH-03 | **출처**:
  - https://screensdesign.com/showcase/huckleberry-baby-child
  - https://pebbi.co/blog/nara-vs-huckleberry-2026
- **도메인 관계**: 타도메인, 인접 (같은 job: 인생에서 가장 정서적인 이벤트를 몇 초 단위로 기록·확인)
- **해결한 문제**: 정서적 도메인의 로깅 도구가 어느 얼굴을 할 것인가 — 같은 job에 정반대 답 2개
- **메커니즘**: Huckleberry는 홈을 '밝은 색 카테고리 타일' 격자로 만들어 **색이 곧 카테고리 식별자**(색=기능). Nara는 홈에서 색을 빼고 **큰 터치 타깃 + 단일 타임라인 뷰**만 남김. 두 제품 모두 정서를 '장식'으로 뿌리지 않고, Huckleberry는 색을 기능에 붙여서, Nara는 여백에 위임해서 처리
- **이식 가능성**: 조건부 — Nara 방향(타임라인 1개, 큰 타깃, 색 없음)이 우리 사용 맥락(주 수회·수십 초·회신 확인)과 정확히 일치. Huckleberry의 색-타일 격자는 우리 모임 20~30개에 적용 시 색이 20종 필요해져 붕괴
- **안 가져올 것**: Huckleberry의 다색 타일 격자(항목 수가 늘면 색 어휘가 고갈), 온보딩과 본편의 스타일 불일치(출처가 "onboarding feels dated"로 지적)
- **실측값**: **확인 불가** — 두 출처 모두 스크린샷만 있고 토큰·hex·크기·간격 정보 없음. **이 카드는 실측값 없는 구조 관찰 카드로 취급할 것**
- **종류 수**: **확인 불가**
- **모바일 성립 여부**: Nara 방향 성립 / Huckleberry 색-타일은 우리 항목 수(20~30)에서 **불가**

> **"정서를 어디에 좁혀 넣는가"에 대한 답**: 두 제품 모두 정서를 전면에 두지 않는다. Huckleberry는 색을 기능 식별자로 소진시켜 정서 여지를 없앴고, Nara는 "too clinical, too busy"를 피하는 방식이 장식 추가가 아니라 **제거**였다. 즉 정서적 도메인의 도구에서 "따뜻함"은 **추가된 요소가 아니라 덜어낸 결과**로 나타난다.

### ref-05 · 한글 세리프의 실제 결과 (네이버 모바일 타이포 연구 · KRDS) · [축 3]
- **채널**: CH-03 + CH-04 | **출처**:
  - https://brunch.co.kr/@chulhochoiucj0/34
  - https://www.krds.go.kr/html/site/style/style_03.html
- **도메인 관계**: 타도메인 (같은 job: 한글 화면에서 무드용 서체를 쓸 때의 대가 계산)
- **해결한 문제**: "예식 정서 = 세리프"라는 반사적 선택의 실제 비용
- **메커니즘**: 명조(세리프)를 본문에서 배제하고 **제목·인용·행사 안내 등 짧은 문장에만 국한**한다. 근거는 심미가 아니라 측정 — 네이버 모바일 본문 연구에서 바탕체(명조) 대비 돋움체(고딕) 가독성이 우수. KRDS도 본문 서체를 산세리프 1종으로 고정
- **이식 가능성**: 가능 — "세리프를 쓰되 본문에는 안 쓴다"는 경계선이 그대로 우리 제약
- **안 가져올 것**: 세리프를 화면 전체 인상 도구로 쓰는 것. 한글 명조는 라틴 세리프보다 획 대비가 크고 x-height가 낮아 15~17px 본문에서 획이 소실됨
- **실측값**:
  - 본문 산세리프 최소 **15~17px**
  - 모바일 적정 행간 **150~155%** (인쇄매체보다 촘촘)
  - **한글 본문 자간 −0.3px 권장**(16~17px 기준) — 라틴과 반대 방향
  - 모바일 좌우 여백 **16~24px**
  - 단락 간격 = 본문 크기의 **75%** (16px 본문 → 12px)
  - 세리프 허용 구간 = 제목 · 1~2줄 이하 · **20px 이상**
  - Pretendard는 타 서체 대비 시각적 크기가 작아 **17px을 기본**으로 사용
- **종류 수**: 서체 계열 최대 2종(본문 산세리프 1 + 디스플레이 세리프 0~1)
- **모바일 성립 여부**: **조건부** — 세리프는 20px 이상 + 2줄 이하에서만 성립

> **실무 주의**: 한글 자간은 라틴과 **반대 방향**이다. 한글 본문은 16~17px에서 −0.3px로 좁혀야 하고(라틴 본문은 보통 0 또는 양수), Linear의 −0.05px 같은 값을 그대로 쓰면 한글에서는 자간이 넓어 보인다.

## 컨벤션 목록 (어기면 사용자가 헤맴)

1. **한글 본문 15px 미만 금지, 행간 150% 미만 금지.** — ref-01(KRDS 본문 17px/150%, 최소 13px), ref-05(모바일 적정 행간 155%). 수십 초 훑기용 화면이라 여기서 아끼면 회신 상태를 오독한다.
2. **본문 대비율 4.5:1 이상.** — ref-01. 저대비 텍스트(Radix 11단계)는 보조 정보에만, 상태 텍스트에는 쓰지 않는다.
3. **면 위계는 명도차로, 최소 3단계.** — ref-02(1=배경 / 3=카드 / 6=구분선). Linear의 4단계 미세 명도차(ref-03)는 모바일에서 소실되므로 단계 수를 줄이고 차이를 벌린다.
4. **액센트색은 1색, 장식 용도 금지.** — ref-03("never decoratively": 브랜드마크·포커스링·주 CTA만). 카테고리마다 색을 주면 항목 20~30개에서 색 어휘가 고갈된다(ref-04 Huckleberry의 한계).
5. **세리프는 20px 이상 · 2줄 이하에만.** — ref-05.
6. **spacing은 4px 배수, 종류는 7종 이하.** — ref-03(4·8·12·16·24·32·48). 종류가 늘면 리듬이 붕괴된다.
7. **위계는 크기가 아니라 weight로.** — ref-01(크기 4종에 weight 2종만으로 전 위계 처리). 크기 종류를 늘리는 것보다 저비용이고 고밀도에서 안전하다.

## 기대했는데 안 나온 것 (= 채널 사각지대)

1. **국내 상업 앱의 실제 타이포 실측값.** uibowl이 막혀서 CH-04 규범 문서(KRDS)로 대체했다. KRDS는 정부 접근성 기준이라 상업 앱보다 보수적일 가능성이 크다(본문 17px은 토스·당근류의 관행보다 클 수 있음). **CH-01 사각지대이자 이 축의 가장 큰 미확인 구간.**
2. **웨딩 카테고리의 실제 시각 사양.** WebSearch로는 기능 비교 기사만 나오고 디자인 분석이 전무. 로그인 벽(CH-02 불가) + 큐레이션 갤러리 미노출. **→ 클리셰 판정을 지금 하면 근거 없는 판정이 된다.** Mobbin/Refero 로그인 세션이 있으면 이 한 건만 재소싱 권장.
3. **디자인 시스템 공식 문서의 컴포넌트 실측치(Apple HIG, Material 3).** 둘 다 JS 렌더링이라 WebFetch로 뚫리지 않음. 리스트 아이템 높이·터치 타깃 최소값(44pt / 48dp)은 통념으로는 알지만 **이번 소싱에서 1차 출처로 확인하지 못했다 — 실측값으로 인용하지 말 것.**
4. **정서적 도메인 중 장례·상조, 반려동물 건강관리.** 육아(ref-04)까지만 닿았고 나머지 두 인접 도메인은 미도달.

## 축 3에 대한 소싱 단계의 잠정 관측 (판정 아님)

양 끝 중 어느 쪽이라는 판정은 하지 않는다. 다만 소싱에서 반복 관측된 것은, **정서적 도메인의 도구 제품에서 "정서"가 추가된 요소가 아니라 제거의 결과로 나타난다**는 점이다(ref-04 Nara, ref-03의 "never decoratively", ref-05의 세리프 격리).

세 레퍼런스 모두 정서를 **한 지점에만** 허용했다 — Linear는 액센트 1색을, ref-05는 20px 이상 제목을, Nara는 여백을.

> 축의 좌표를 정할 때 "얼마나 정서적인가"가 아니라 **"정서를 허용하는 지점이 몇 개인가"** 로 물으면 관측 가능한 값이 된다.
